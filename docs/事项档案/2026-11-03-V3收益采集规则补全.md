# V3 收益采集规则补全

日期：2026-11-03。用户确认“那就补充完”后实施。本事项仅补收益采集后端、隔离检查与接入交接，统一面板由另一会话负责。

## 已完成

- 正常按日来源采到昨天；同一账号、剧场、适配器及日期的成功/明确无数据结果复用，失败可重试，开发模拟日志不阻止真实采集。
- 首次按日倒查连续 7 天明确零/青柠正常空记录停止；失败打断连续计数。每账号每轮最多新读 90 天；独立保存起点、停止边界及完成标志，中断和读取上限均保留续采能力。
- 累计首次金额暂入实际采集日，以后只入新增差额，漏采恢复归恢复当天；同日显式重读不重复记全额。原金额、来源周期、采集时间、尝试编号留在快照和日志中。
- 真实支持月份的采集器可通过 `MONTHLY_FETCHERS` 首次读本月、上月、上上月；多月分别计算后合并到采集日，避免同日覆盖。明确的月周期跨月另起基线。首次补采跨月仍保留原月份，已保存的月中累计在月结后再读一次结清增量。
- 来源周期不明确或累计下降时不猜测清零，不覆盖原基线；无效金额、网络/解析失败不造 0，不抹去已有成功收益。
- 青柠默认不保存视频明细；完整分页、记录数与总计校验、显式保存路径保留，旧明细不删除。
- 收益同时写现有兼容日收益表与 `v3_revenue_account_periods`，驾驶舱读模型无需触发采集即可读取真实来源的新结果。
- 手动和自动入口共用现有收益任务；重复点击复用活动收益任务。首次总量为读取上限，结束后按实际读取数收口，并保留历史未补齐说明。
- 按北京时间确定采集日、调度日期及批次时间；新增两张状态表在新库与现有版本初始化路径中均可创建，不清库、不改已有表结构或版本号。

## 当前来源能力与限制

| 来源 | 现有实现 | 不能据此宣称的能力 |
|---|---|---|
| 青柠 | 按日分页、明细解析与总额核对 | 本轮未做线上有效性核验 |
| 顶好 | 指定日期的账号总额；返回 0 仍按不确定处理 | 不能将不确定 0 用于停止首次倒查 |
| 触摸、花生 | 当前累计查询；快照与差额入账 | 当前解析未提供可靠月份/历史月份参数，不会假造前三月数据 |
| 其他剧场 | 能力接口标未接入 | 本轮没有新增其网站采集实现 |

已有旧累计成功日志只用于衔接原金额基线，不批量修复旧版本已经保存的历史收益。当前周期未知的来源跨月下降时会失败待核对，需后续获得真实周期依据后补适配器能力。

## 给统一采集界面会话的接入约定

前端不用重复实现首次补采、差额、去重或逐剧场日期策略。

1. `GET /api/v2/revenue/collectors`：返回 `items`、`supported_theaters`、`backfills`。每剧场提供 `adapter_status`、`date_precision`、`supports_month_query`、`supports_detail`、`detail_persistence_enabled`、`runtime_verified` 和说明。`ready` 只表示已有代码，`runtime_verified=false` 表示本轮未核验线上。
2. `POST /api/v2/revenue/collect`：使用已有收益任务入口，传 `start_date`、`end_date`（正常都传北京时间昨天）、`theaters`、`account_ids`。`initial_backfill` 默认 true，后端判断是否需要补历史；明确的手动日期区间操作可传 false。省略筛选表示全部已有适配器，空数组表示不选择任何项。
3. 返回 `run_id`、`status`、`total_units`；若已有收益任务，返回原任务和 `reused=true`。第一次倒查的总量是上限，完成后会收口。
4. `GET /api/v2/revenue/collection-runs/{run_id}`：沿用状态、完成数、成功/空/失败数、当前剧场/账号及 `error_message`。`completed` 表示本轮结束，未补齐说明不能隐藏；具体首次完成状态从能力接口 `backfills` 读取。
5. 日志与数据继续使用 `/api/v2/revenue/collection-logs`、现有日收益接口；驾驶舱重读 `/api/v3/operations-dashboard`。累计增加额属于采集日，前端不拆补回漏采日。
6. 统一面板后续在现有 `server/collection_jobs.py` 的任务调度下复用收益执行体与上述能力；本轮没有给面板新增另一套任务系统，也没有完成收益类别的前端接线。需在真正接线时协调停止/继续、全局活动任务与收益批次，不能同时启动两次同账号收益查询。

示例请求（日期按实际当天计算）：

```json
{"start_date":"2026-11-02","end_date":"2026-11-02","theaters":["青柠剧场"],"account_ids":["账号ID"],"initial_backfill":true}
```

## 后续新增剧场在哪里做

- `server/v2_revenue_service.py`：`REVENUE_ADAPTERS` 登记能力，新增抓取/解析函数并在 `_fetch()` 分派；真实支持指定月份时登记 `MONTHLY_FETCHERS`。已有触摸/花生不能只修改能力标志就当支持月份。
- `server/revenue_collection_state.py`：共用补采状态、累计快照和日期入账规则，一般无需随剧场复制。
- 新来源需补正常金额、明确空/零、解析/请求失败、分页与周期切换检查，并另做真实来源核对。采集界面不随每个来源重新开发一套流程。
