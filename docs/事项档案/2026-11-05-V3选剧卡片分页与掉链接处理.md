## 用户目标与最终行为

入口仍为顶部“安排今天”→选挂载方式、账号→“选择剧集”。

1. 修复翻页时先卸载整块卡片、加载文字挤压高度而引起的跳位和闪动。保留旧页直到新页读取成功，加载状态在固定行中显示；列表固定高度并独立滚动，最后一页不足20部时不收缩，翻页栏在列表外保持位置。弹窗主滚动区关闭浏览器滚动锚定并预留滚动条宽度。不同账号/来源/关键词/范围的旧结果不混入新范围，加载期间禁止选择旧线上结果和重复翻页。
2. 将只能前后翻页改为“上一页＋直接选页码＋当前页/总页数＋下一页”，每页20部；越界请求归到最后一页。
3. 卡片采用左侧72×100封面、右侧单行缩略剧名和状态，常规窗口4列、宽屏5列，极窄窗口2列。保留悬停完整剧名和跨页勾选，列表提示本页可滚动。
4. 卡片右键打开“复制剧名”，点击复制完整名称并提示，不触发勾选。ESC先关闭菜单；菜单聚焦不滚动页面，用户在外部点击或滚轮操作时关闭。
5. 共用DramaCover组件有有效图片时不叠加缩略剧名及为文字添加的遮罩；无图片/加载失败保留剧名占位，新图片地址可重试。图片自身文字、人工编辑文字、生产中心剧集/羊头类型标记和编辑操作提示保留。
6. 重新获取后逐账号×来源核对完整目录：本轮未返回的旧编号标为不在架、不可挂载，线上“可挂载/全部”和可选候选均隐藏；小程序/视频号方式的“现有剧集”也只显示全部所选账号都有可用资料的剧。刷新候选后清除不再可选的勾选，后端再次拒绝过期挂载编号。重新上架时恢复同一关联，不重复新建。

## 用户实测反馈后的修复（2026-11-05）

### 已确认根因与实际恢复

用户实测提示平台报告140部、获取0部且中断，列表为空。对正式数据库使用SQLite只读连接检查：v3_catalog_entries有140部视频号剧，目标账号v3_catalog_availability有140条usable=1，表中没有本次新增的present列。正式8782接口实查返回HTTP400、no such column: a.present，证据为local-test-output/catalog-picker-repair-20261105/live-before.json。

根因是原有升级流程只在缺少功能表时调用目录初始化；已有数据库版本号13、所有功能表都存在时跳过了新增列迁移。之前直接调用初始化的测试覆盖不了这一真实启动路径，是本次修改遗漏，并非平台删除了全部剧目。

已修复：server/v2_file_service.py在现有表齐全时仍执行目录字段检查；server/drama_catalog.py抽出ensure_availability_schema，构造目录服务时兼容已缓存连接，迁移和提交加锁，避免并发重复加列。字段已存在时只读检查，不重复运行建表或更改业务记录。

本次为恢复该故障，先用SQLite一致性备份保存正式库到local-test-output/catalog-picker-repair-20261105/formal-db-before-presence.sqlite3，然后只执行ADD COLUMN present INTEGER NOT NULL DEFAULT 1。未运行整个业务库初始化、未改已有字段值、未触发正式平台查询或重新获取。账号、剧集、目录条目、账号可用记录、关联和任务六类表修复前后旧字段的全量行哈希及条数一致；quick_check为ok。正式接口随后返回HTTP200、总数140；挂载候选接口返回140条。记录为live-repair.json。没有重启正式进程；当前进程仍沿用上一轮每页20逻辑，数字分页及可选页数需要正常重开开发版后加载新源码。

备份仅作正式故障恢复证据，不作为测试库使用，不进入安装包。无恢复需求时不主动回退；确需恢复时须先正常停止软件并另行确认期间新增数据的处理，不能把此备份覆盖到正在写入的数据库。

## 按剧场展示现有剧集及边获取边创建（2026-11-05）

用户实测明确区分：现有剧集展示账号所属剧场完整剧库，小程序/视频号页签展示当前账号的挂载目录；同剧场账号即使挂载关系不同，现有剧集也应相同。随后补充获取期间允许选择已获取的剧集并直接创建任务。
