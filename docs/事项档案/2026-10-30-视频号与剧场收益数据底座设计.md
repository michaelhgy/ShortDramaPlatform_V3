## 一、先定清楚数据关系

系统里不是两套并列的“官方数据”和“小V猫数据”。实际链路是：

```text
视频号官方后台
    ↓
小V猫登录的官方后台与 MCP 采集层
    ↓
V3 保存采集运行、快照和原始返回
    ↓
看板只读取 V3 本地数据
```

因此字段中必须同时记录：

- `source_system`：真正的数据来源，例如 `video_official`、`theater_qingning`。
- `acquisition_layer`：通过什么方式拿到，例如 `xiao_v_mcp`、`theater_web`。
- `storage_layer`：当前存在哪里，例如 `v3_snapshot`、`v2_legacy`。
- `collection_run_id`：哪一次采集产生的。
- `fetched_at`：实际读取时间。
- `data_state`：这次结果是有记录、明确为零、无数据、失败、失效还是仅缓存。

小V猫不是完整历史数据库。它只返回当前已有缓存，或者在用户明确触发时向官方后台获取指定范围。V3 当前保存的也只是若干采集批次，不代表官方全量历史。

## 二、两个数据域

### A. 视频号数据域

这部分回答“账号和作品在视频号官方后台表现如何”。首版看板需要以下事实表和状态表：

| 表/对象 | 粒度 | 用途 |
|---|---|---|
| `video_accounts` | 一个视频号账号 | 账号身份、UID、登录和有效状态 |
| `video_account_daily` | 一个账号 × 一个统计日 | 昨日流量、近 7 日趋势、账号排名 |
| `video_posts` | 一个账号 × 一个官方作品 | 作品身份、发布时间、发布状态、最新累计指标 |
| `video_post_daily` | 一个作品 × 一个统计日 | 每个账号最高播放、全账号播放 Top 10 |
| `video_account_diagnostics` | 一个账号 × 一次诊断结果 | 异常账号和减少推荐等问题 |
| `video_post_punishments` | 一个作品/导出 ID × 一条处罚记录 | 处罚、减少推荐等具体问题 |
| `video_collection_runs` | 一次采集请求 | 采集范围、是否触发官方刷新、运行结果 |
| `video_collection_items` | 一次采集 × 一个账号/数据日 | 逐账号、逐日期成功/失败/无记录状态 |

暂不进入该数据域：直播状态、订单/佣金/带货、商品和店铺、评论和私信。它们虽然在 MCP 能力里存在，但已明确排除。

### B. 剧场收益数据域

这部分回答“各剧场查询网站返回了多少收益，以及能细到什么程度”。它不能假定所有剧场都能按天、按剧、按视频统计。

| 表/对象 | 粒度 | 用途 |
|---|---|---|
| `revenue_sources` | 一个剧场 | 查询地址、查询方式、时间粒度和明细能力 |
| `revenue_collection_runs` | 一次收益采集请求 | 采集批次和进度 |
| `revenue_collection_attempts` | 一个剧场 × 一个账号 × 一次查询 | 记录网页查询、返回状态和错误 |
| `revenue_account_periods` | 一个账号 × 一个剧场 × 一个统计周期 | 统一保存金额，不伪造日期 |
| `revenue_details` | 一个剧场返回的一条明细 | 青柠等有详细结果时保存剧名、视频、播放和金额 |

收益数据和视频号流量数据在底座中并列存在。只有在两个来源都有明确的日期、账号和关联键时，界面才允许做对照；不能因为都有“收益”和“播放”两个词就强行拼成因果关系。

## 三、视频号字段契约

### 1. 视频号账号

| 字段 | 来源字段/含义 | 必填 | 说明 |
|---|---|---:|---|
| `account_id` | V3 内部账号 ID | 是 | 关联本地账号资料 |
| `uid` | 视频号官方 UID | 是 | 官方侧稳定标识 |
| `account_name` | 小V猫返回昵称 | 否 | 昵称会变化，不能作为主键 |
| `platform` | `Channels`/视频号 | 是 | 当前只保留视频号 |
| `login_status` | 小V猫账号登录状态 | 是 | 采集时状态，不代表永久状态 |
| `fans_total` | 账号快照粉丝总量 | 否 | 必须带快照时间 |
| `group_ids` / `tag_ids` | 小V猫组织信息 | 否 | 用于筛选，不作为业务指标 |
| `seen_at` | 账号被小V猫看到的时间 | 是 | 识别共享小V猫带来的账号变化 |

### 2. 账号每日统计

主键建议为 `uid + stat_date + collection_run_id`，分析读取时选择该日期最新且状态可用的一条。

| 字段 | 小V猫实际字段 | 说明 |
|---|---|---|
| `stat_date` | `daily.date` | 统计日，不是采集日 |
| `view` | `daily.view` | 账号当天播放量 |
| `fans_total` | `daily.fansTotal` | 当日粉丝存量 |
| `fans_add` | `daily.fansAdd` | 新增粉丝 |
| `fans_net` | `daily.fansNet` | 净增粉丝 |
| `fans_reduce` | `daily.fansReduce` | 掉粉 |
| `like` | `daily.like` | 点赞 |
| `favorite` | `daily.favorite` | 收藏 |
| `comment` | `daily.comment` | 评论 |
| `forward` | `daily.forward` | 转发 |
| `payload_json` | 原始 MCP 返回 | 保留原文，便于字段变化后复核 |

### 3. 作品与作品每日统计

作品名称不能假定为剧名。当前真实返回中标题全部为空，只有少量描述有值，因此作品在界面上显示“作品标题未返回”，并提供“未关联剧集”状态。

| 对象 | 字段 |
|---|---|
| 作品身份 | `post_id`、`uid`、`account_id`、`post_time`、`post_type`、`publish_status`、`timing` |
| 作品内容 | `title`、`desc`、`cover_present`、`url_present` |
| 作品累计指标 | `view`、`like`、`comment`、`forward`、`love`、`fans_add`、`full_view`、`view_time` |
| 作品每日指标 | `stat_date`、`view`、`like`、`comment`、`forward`、`favorite`、`fans_add` |
| 详情字段 | `video_time`、`updated_at`，有返回才保存 |
| 证据字段 | `metric_grain`、`source_kind`、`fetched_at`、`payload_json` |

作品排行必须先明确粒度：

- 每个账号最高播放视频：按同一个统计日的 `video_post_daily.view` 分账号取最大值。
- 全账号播放 Top 10：按同一个统计日的 `video_post_daily.view` 全局排序。
- 没有作品分日数据时，不能把累计 `video_posts.view` 当成昨日播放。
- 账号总播放和作品播放不相加，两个接口的统计口径可能不同。

### 4. 诊断和处罚

保留账号是否异常、是否验证、视频状态、热度状态、异常作品数、最后诊断时间，以及处罚作品的账号、导出 ID、发布时间和处罚状态。`live_status` 即使官方返回，也不进入产品数据表。

## 四、收益字段契约

### 1. 剧场查询能力

每个剧场先建立一条来源配置，不能把四个剧场写成同一种接口：

| 字段 | 说明 |
|---|---|
| `theater_id` | V3 剧场 ID |
| `adapter_key` | 具体查询适配器 |
| `query_url` | 查询地址 |
| `query_mode` | 日期查询、日期范围查询或月累计查询 |
| `date_precision` | `day`、`month`、`unknown` |
| `supports_detail` | 是否返回视频/剧目明细 |
| `requires_account_id` | 是否需要输入账号 ID |
| `requires_date` | 是否需要选择日期 |
| `last_checked_at` | 最近一次查询时间 |
| `adapter_status` | 已接入、待配置、失败、停用 |

### 2. 账号周期收益

统一表使用周期字段，不强制使用 `revenue_date`：

| 字段 | 说明 |
|---|---|
| `account_id` / `theater_id` | 本地账号和剧场 |
| `period_label` | 页面返回的原始周期文字 |
| `period_start` / `period_end` | 能确认时填写，否则为空 |
| `period_type` | `day`、`date_range`、`month_cumulative`、`unknown` |
| `amount` | 返回金额 |
| `currency` | 默认人民币，但仍保存 |
| `data_state` | 成功、明确零、无数据、失败、不确定 |
| `settlement_state` | 未结算、已结算排除、未知 |
| `source_attempt_id` | 对应具体查询尝试 |
| `raw_result_json` | 原始解析结果 |

当剧场只返回“本月累计收益”时，只写一条 `month_cumulative` 记录，不拆成每日金额、不伪造日期，也不关联到某个作品。

### 3. 收益明细

青柠可以保存 `source_video_id`、`source_drama_name`、`video_views`、`drama_views`、`gross_revenue`、`source_rank`、`match_status`。其他剧场没有这些字段时保持空值，不能用青柠字段补齐。

已结算月份不进入当前未结算流水卡片；已结算数据可以作为历史留档，但必须通过 `settlement_state` 排除。

## 五、统一采集状态

所有数据域统一使用以下状态语义：

| 状态 | 含义 | 看板处理 |
|---|---|---|
| `record` | 正常返回有效记录 | 可统计 |
| `confirmed_zero` | 来源明确返回零 | 可统计为 0 |
| `no_data` | 来源正常，但没有记录 | 不当作 0，显示无数据 |
| `unavailable` | 账号不存在、作废或登录失效 | 不进入总量，显示失效 |
| `failed` | 网络、解析、校验或接口失败 | 不进入总量，显示失败 |
| `cached_only` | 只读取小V猫本地缓存，未确认本次官方刷新 | 可展示，但标注缓存 |
| `partial` | 只有部分字段或部分日期 | 按覆盖率展示 |
| `not_collected` | 当前还没有执行采集 | 显示待采集 |

采集运行还要记录 `requested_start_date`、`requested_end_date`、账号范围、是否触发官方刷新、开始/结束时间和逐项错误。页面读取和分析过程不触发小V猫刷新。

### 已发现的数据质量问题

1. 作品缓存包含 10 个 UID，但当前有效账号清单只有 9 个，说明缓存中存在历史账号或跨批次记录。作品表必须保留采集时账号状态，不能只靠当前账号表内连接。
2. 作品标题不返回，剧名不能从小V猫作品字段推断；收益剧名只能来自剧场明细或人工关联。
3. 账号统计、作品累计指标、作品分日指标不是同一粒度，不能直接相加或互相替代。
4. 旧数据库同时存在真实收益历史、账号快照和模拟作品数据，必须靠 `source_kind` 和 `data_state` 隔离，不能按表名直接信任。

## 七、首版采集范围

为了先完成看板，不继续扩大采集面，首轮只需要：

### 视频号

- 账号清单和登录状态
- 账号昨日及近 7 日每日统计
- 作品列表及累计指标
- 作品每日指标或作品趋势 Top 数据
- 账号诊断和处罚作品
- 采集运行和逐项状态

### 剧场收益

- 每个已启用剧场的查询配置
- 每个剧场至少一次真实查询结果
- 账号周期收益金额
- 青柠等有明细剧场的明细
- 其他剧场的金额、周期精度和覆盖状态
- 收益采集运行和错误记录

以下数据暂不采集：直播状态、订单/佣金/带货、商品和店铺、评论和私信。

## 八、进入看板开发的条件

满足以下条件后才开始改看板：

1. 视频号和收益两套字段契约落地，读取层不再直接依赖旧模拟数据。
2. 视频号首轮真实快照能够区分缓存、刷新成功、无记录、失败和失效。
3. 各剧场至少标记清楚按日、按月累计或未知周期，收益卡片不再把所有剧场画成同一条日趋势。
4. 看板展示每个数据块的更新时间和覆盖状态。
5. 账号最高视频和全账号 Top 10 只使用小V猫作品数据，并明确统计日期和指标粒度。
