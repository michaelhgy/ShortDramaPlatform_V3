## 1. 使用背景与目标

这是短剧推广运营工具。正式运营预计约20个账号，每个账号约300～400条视频。账号分别关联剧场，收益来源和查询能力随剧场不同。

软件已有经营总览、账号矩阵、账号优化、作品表现和数据导出等业务内容。它们依赖本地保存的数据，采集负责取得或更新这些数据。

用户同时需要：

- **方便**：常规使用少操作，由软件判断哪些数据已经完整、哪些缺失，不需要用户反复记住上次采到哪里。
- **自由**：能只处理一部分账号、只处理某类数据、只更新指定范围；不能为了简单把所有类别强行一起全量采集。
- **节制**：减少重复、无意义的外部请求，控制耗时和资源消耗，降低触发平台限制的机会。
- **透明**：知道在查谁、查什么、查到哪一步、为什么跳过、哪些有结果、哪些失败或仍缺失。
- **可信**：没有数据就是没有；不能填模拟值、把失败变成零、用旧缓存冒充刚刷新。

工作台的显示日期和采集日期是不同概念；查看或筛选已经保存的数据，不应自动触发外部采集。数据日期按业务时区Asia/Shanghai理解。

## 2. 要处理的数据及业务规则

### 2.1 账号日数据

**它是什么**

账号每一天的官方统计，覆盖账号全部来源的作品，不限V3发布。主要已有字段：

| 字段含义 | 说明 |
| --- | --- |
| 总计播放量 | 该账号当天的播放量 |
| 关注者总量 | 当日关注者存量，来源可缺失 |
| 新增关注 | 当日新增 |
| 取消关注 | 当日取消 |
| 净增关注 | 可以为负数 |
| 爱心数 | 与点赞分开 |
| 点赞数 | 与爱心分开，不解释成收藏 |
| 评论数 | 当日评论 |
| 分享数 | 当日分享 |

**主页访问不需要，已经要求全部移除，不再采集、展示或导出。**

**更新规则**

- 日常按账号、日期补齐截至昨天的数据。
- 某账号某日已有完整有效数据，后续普通采集不再获取该日。
- 有部分字段不等于该日完整，已知字段保留，仍需补缺。
- 用户可以明确要求重新获取已有日期，但强制重取必须限定所选账号和日期，不能把其他类别也一起强制刷新。
- 首次需要向前补齐可取得的历史。既有业务处理以最早非零活动日前连续7天完整全零作为推定历史边界；缺失、失败不算全零，边界未确认就不能宣称历史完整。这不是官方注册日期。
- 首次或后续补采中断，已经取得的数据保留，之后继续补缺。
- 强制重取失败，原有有效数据保留。

**来源特点**

先核对V3已经保存的数据；需要补的部分先读小V猫已有数据，不足时主动请求小V猫刷新再读取。小V猫不会保证自动拥有官方最新数据，不能把“读过小V猫”当成“已主动刷新官方”。

该数据用于账号日流量明细/导出以及工作台相关账号、区间流量统计。

### 2.2 账号视频数、关注者数

这是账号当前显示的作品数量、关注者总量，与账号日数据中的“当日关注者存量”不是同一条记录。

- 用户要求顺带取得，不希望每次把它当成独立采集任务来安排。
- 适合与哪一步复用请求，由后端根据实际返回字段判断，不人为重复请求。
- 当前可从小V猫已有账号统计资料读到视频数、关注者数和来源更新时间，不保证是刚从官方刷新的实时值。
- 本次没有新资料，不能把旧资料更新时间改成本次时间，不能因缺失而填零。

它们用于账号卡片、账号详情等基本经营信息。

### 2.3 视频最新累计流量

**它是什么**

每条作品当前累计指标，覆盖账号全部来源的作品，不限V3发布。现有数据包括：

- 账号、作品ID、发布时间。
- 累计播放、爱心、点赞、评论、分享、作品带来关注。
- 完播率、平均播放时长；来源未提供时保留缺失。
- 作品封面、播放地址、视频时长。
- 实际取得数据的时间。

作品名字：明确关联V3发布记录时，显示对应视频的实际文件名；没有关联时显示作品ID，不自行创造作品标题。取得作品自己的在线封面后可缓存到本地并替换原剧集封面。点击封面播放保存的视频地址；地址可能失效，后续采集能够更新。播放失败本身不触发全账号采集。

**更新规则**

- 支持选账号，全量更新这些账号的作品。
- 也需要支持按作品发布时间范围更新，例如最近七天或指定起止日期。
- 日期范围筛的是“哪些时候发布的作品”，采的是这些作品**现在的累计值**，不是它们在所选日期内新增的播放。
- 用户认可的节省请求方式：作品按发布时间从新到旧分页，获取到时间范围下界所在页后，处理本页符合范围的作品，停止继续翻页。不能先全量获取再本地过滤，却声称减少了请求。
- 时间排序和置顶作品是否影响停止条件，仍需采集器核实。日期范围的具体边界必须可明确理解；默认几天不是已确认要求。
- 仅更新部分作品，不清除范围外的旧数据，也不能据此把范围外作品判断为删除。
- 最新数据有价值，但不能持续全量刷新。用户可以主动选择更新范围，并控制重复更新和逐页请求节奏。
- 翻页等待要在设定范围内随机变化，不是每页固定等同样的秒数。具体可支持参数由后端校验。
- 近期作品、仍有较大流量的旧作品可能更有更新价值；这属于设计时需要考虑的运营场景，目前没有已确认的流量阈值或自动筛选公式。

该数据用于作品表现、作品详情及相关累计流量统计。它不能代替账号官方日数据。

### 2.4 优化记录与作品分析

- “原创优化”是优化原因之一，不是与优化并列的另一类事件。按当前业务口径，一个作品对应一个优化原因。
- 需要保存被优化的作品身份、发布时间、优化原因/类型以及“作品分析”的具体文字。具体分析文字用于判断原因，不能只保留一个笼统的“被优化”状态。
- 优化作品会被用户从平台删除，删除后可能无法再查看具体分析，因此已经取得的分析和发布历史必须留在V3。
- 优化率仅统计明确关联到V3发布记录的作品：V3历史发布记录提供分母，匹配到这些发布记录的优化提供分子。
- 归属以明确V3发布记录为准，按账号、真实发布时间等作品身份建立关联，不按标题猜测；具体时间精度由后端核实。未关联V3发布的优化不收录为V3优化记录、不纳入这部分统计；不能用账号当前剩余作品数加优化记录数猜历史分母。
- 已取得的有效分析可以复用，不为同一原因重复请求详情。
- 当前读取小V猫已有诊断并补取详情，不等于本次主动完成一次新的官方诊断；诊断来源时间与本次读取时间不能混淆。

该数据用于账号优化、原因分布和V3发布作品优化率。

### 2.5 剧场收益

收益与其他数据属于同一套采集功能，不能每增加一个剧场就要求用户学习另一套采集流程。来源差异是真实存在的，不能为界面统一而把不同金额口径混为一谈。

**按日来源**

- 正常查询昨天。
- 某账号某日期已取得有效结果，普通采集不重复查询；失败可以重试。
- 明确返回零收益是有效零，未更新、失败、缺失不能当零。
- 支持按日期查询的来源，首次从昨天向前倒查，连续7天明确为零收益后停止。
- 首次中断后接着补齐，不能因为已存了一天就认为首次完成。

**累计来源**

- 首次按该来源能力查询本月、上月、上上月；查不了的月份如实保留缺失。
- 首次取得的金额暂归实际采集日期。
- 后续只将新增差额归采集日期。同一月份的累计金额不能每天全额重复计入。
- 中间漏采，不再把后续差额拆回漏采日期。
- “已有结果不重查”不能解释成累计来源查过一次就永久停止；后续仍需按后端规则取得新的累计数，计算新增差额。

青柠当前以账号日收益为主。视频明细解析、校验、保存能力可以保留，但默认不保存明细。

不同来源返回“暂无记录”“尚未更新”“明确零收益”的语义要由后端区分，不能由前端看到空响应就永久判定完成。累计金额回退等异常处理仍需来源侧核定，不在设计里自行发明金额规则。

收益后端正在另一个会话继续开发。首次判断、倒查停止、累计差额、去重、补采续接、金额归属均由后端处理，前端不能另算一套。前后端正式接入前还需确认接口。

## 3. 必须满足的使用能力

以下是能力要求，不是页面结构或按钮安排：

- 能按实际需要处理全部或部分账号，以及一种或多种数据。
- 能分别理解并设置不同类别真正有效的范围；不能让一个含义不明的全局日期或全局强制刷新改变所有类别。
- 普通使用时软件应知道完整性、缺口和更新价值，不把“该不该重复查”全交给人记忆。
- 在执行前，用户能理解本次将处理什么、可能读取哪些外部数据；不能误以为只更新七天，实际却更新全部。
- 运行中能理解当前账号/来源、正在处理的数据和范围，以及为何需要等待；不能只有一个没有解释的百分比。
- 能辨别新增、更新、复用、跳过、尚未更新、缺失、部分完成、失败和停止。失败或停止不能被当成全部成功。
- 能停止后续请求；当前已发出的请求可能要等返回后才能停。已取得结果保留。
- 能针对未完成部分重试或续采，不能重试一个账号就把其他已完成账号也全部重来。
- 操作重试不应悄悄改变之后正常采集的账号或范围。
- 重复发起同一活动任务不应多排一批。遇到访问限制时应停止或暂停后续请求，不自动高频重试。
- 打开、关闭、查看进度、切换展示筛选，不应偷偷发起新一轮外部采集。关闭界面和停止任务是不同动作，实际行为必须能被用户理解。
- 用户只需说明业务目标和使用感受，不应被要求理解小V猫内部接口、分页游标、数据表等实现细节。

## 4. 用这些情境检验方案是否好用

1. 今天要更新运营数据：有些账号昨天已经完整，有些缺一天，有些首次加入。用户不想逐个记忆、重复选择或全量抓取。
2. 只想更新两个账号近七天发布作品的当前流量：不动其他账号，不连带重查已有日数据和收益，也不翻到全部旧作品。
3. 怀疑某账号某天的日数据有问题：只对这个账号、这些日期重新获取，失败时保留旧结果。
4. 20个账号处理到一半：某账号登录失效，其他部分已经成功。用户需要知道完成了什么，并只处理剩余问题。
5. 收益部分日期已经有有效金额，部分暂未更新，另一个剧场只提供累计值：软件应按各自规则处理，用户不应手动推算差额或重复确认已有日期。
6. 第一次补历史中途停止，稍后再来：已经保存的结果仍在，未补齐的继续，不从头开始，也不误报全部完成。

以下只帮助判断哪些可以真实接通，不要求沿用旧界面：

| 能力 | 目前可以依赖的情况 |

| 账号日数据 | 已有本地优先、缺失主动获取、完整日跳过、历史补齐与保存能力 |
