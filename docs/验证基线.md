## 怎么验证

**双击 `tools\一键验证.bat`**（或者在项目根目录运行 `py -3.12 tools\verify_v2.py`）。

它会做两件事：
1. 跑后端单元测试（`server/tests`，16 个测试文件）
2. 跑前端类型检查（`tsc --noEmit`）

并且**自带隔离**：脚本会把 `V2_WORKSPACE_ROOT` 指向一个临时目录，所以它永远不会读写 `D:\短剧推广运营系统` 里的真实业务数据。

## 那 2 个失败：已修复（2026-09-17）

**历史现象**（修复前）：`server/tests/test_v2_task_center.py` 的 `V2TaskCenterExecutorOwnershipTests` 有 2 个测试失败，导致基线长期是"142 通过 / 2 失败"。

- `test_observing_output_is_presented_as_an_active_export`
- `test_snapshot_keeps_a_complete_executor_payload`

**根因**：这两个测试没有自建临时数据库，会去连接"当前环境配置的数据库"。而同一个测试进程里，前面的 `V2FileServiceTests` 会把模块级全局变量 `WORKSPACE` / `DATA_ROOT` / `DATABASE_INITIALIZED_PATH` 指向它自己的临时路径，`tearDown` 只删了临时目录却没把全局复位；等轮到这两个测试时，路径已被删除，于是报"无法打开数据库文件"。**属于测试之间互相污染，不是产品缺陷。**

**修复方式**（只改测试文件，未动生产代码）：
1. `test_v2_file_service.py`：`setUp` 先保存 3 个全局变量的原值，`tearDown` 恢复后再清理临时目录（治本，堵住泄漏源）。
2. `test_v2_task_center.py` 的 `V2TaskCenterExecutorOwnershipTests`：自建临时工作区并复位（防御，这两个测试不再依赖执行顺序）。

方案全文见 `docs/试点方案-测试隔离修复.md`。

⚠️ **修复注意事项（依旧有效）**：**不能**靠"让环境里的数据库能打开"来修——那样这两个测试就会把建表语句写进**真实生产库**。必须给它们自建临时库。

## 危险提醒

1. **不要**直接在项目根目录跑 `pytest server/tests`（不带隔离）。2026-09-17 已发生过一次：测试触碰了生产库（执行了幂等的建表/建索引语句；事后核验 integrity ok、无外键违规、文件大小未变）。此后一律用一键验证脚本。
2. **测试通过 ≠ 功能可用**。本基线只覆盖单元测试与类型检查，属于**证据等级 2**。剪映真实行为、打包后运行、界面操作都不在其中，必须另外人工验证。

## 怎么判断"改坏了没有"

1. 改动**前后各跑一次**一键验证，比较结果。
2. 后端必须 **161 通过 / 0 失败**；出现任何失败 → 视为**回归**，先查原因再继续。
3. 前端类型检查必须保持**通过**。
4. 涉及剪映导出、打包、界面行为的改动，本脚本覆盖不到，**必须另外人工验证**并单独说明证据等级。
