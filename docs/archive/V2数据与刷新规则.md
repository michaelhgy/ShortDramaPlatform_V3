## 1. 总原则

1. SQLite 数据库和后端实际执行结果是业务事实的唯一来源。
2. 文件系统是媒体文件是否存在、大小、时长和分辨率的事实来源。
3. React 界面只负责显示和发起操作，不自行猜测任务状态，不直接操作文件，不把 Mock（模拟数据）当真实数据。
4. V1 是独立产品线。V2 不读取 V1 运行时数据库，不调用 V1 作为运行时服务。
5. 缓存只能用于加快首次显示，不能替代后端事实，也不能永久覆盖新数据。

## 2. 统一任务状态

所有后台工作都必须记录统一的任务信息：任务类型、所属账号、所属剧集、当前步骤、状态、开始时间、完成时间、错误原因、最近更新时间和重试次数。

状态至少包括：

- 排队中：已提交但尚未开始；
- 执行中：执行器正在处理；
- 成功：当前步骤已完成；
- 失败：当前步骤明确失败；
- 超时：超过对应执行器的超时时间；
- 暂停：执行器或任务被人工暂停；
- 已取消：任务被明确取消；
- 已完成：整个业务流程完成，例如登记发布。

失败、超时和人工中断必须保留错误原因及时间，不能只在界面显示一个“异常”。

## 3. 摘要和详情

### 3.1 列表摘要

生产中心左侧任务卡、任务中心列表和小型任务窗口使用摘要数据。摘要必须一次返回显示列表所需的完整统计，不依赖用户打开详情或鼠标移动触发请求。

每个账号 × 剧集摘要至少包含：

- 素材总数和待扫描数量；
- 模板草稿排队、生成中、已生成、导出中、已完成、异常；
- 成片草稿排队、生成中、已生成、待导出、导出中、已导出、异常；
- 当前执行步骤和执行器；
- 总数、完成数、异常数；
- 计划发布时间、发布登记状态；
- 最近更新时间。

左侧所有状态、数字和颜色进度条只使用这份摘要，不能一部分读摘要、一部分从未加载的详情数组重新计算。

### 3.2 详情

打开剧集后，才读取该剧集的完整素材、草稿、视频、文件和错误信息。详情接口必须按任务编号查询，不能为了找一条详情而读取全部剧集。

详情缓存可以立即显示，但打开后必须后台静默校验最新数据。任务操作完成、重试、重新生成、重新导出、扫描素材和登记发布后，要主动刷新当前任务详情及对应摘要。

## 4. 刷新规则

1. 首次进入页面：先显示内存或本地缓存，再请求最新摘要；请求返回后原子替换，不在请求期间清空旧内容。
2. 页面切换回来：保留已加载内容，后台检查变化，不重复加载全部详情。
3. 有运行任务：优先更新正在变化的任务；没有变化时不重绘全部页面。
4. 没有运行任务：低频校验即可。
5. 页面隐藏、软件从后台恢复、电脑从休眠唤醒或本地服务重启后：主动刷新一次摘要，并重新连接服务。
6. 请求失败：保留最后一次有效数据，显示更新失败提示；不能把页面变成空白或把真实数字改成 0。
7. 定时刷新只是防止通知丢失的兜底方式，不应依赖高频全量扫描。

## 5. 变化通知

后端状态发生变化时，应产生一条轻量变化记录，至少包含任务编号、变化类型和更新时间。界面收到变化后只更新受影响的任务。

变化类型包括：任务创建、状态变化、数量变化、文件扫描、导出结果、失败或超时、重试、发布登记、撤销登记和清理。

当前阶段可以使用本地服务的短轮询实现；后续可替换为本地事件通知，但页面和业务规则不应因此改变。

## 6. 页面职责

- 生产中心：显示账号 × 剧集的生产摘要和当前剧集详情。
- 任务中心：显示三个执行器及其他后台任务的统一状态，不重新推断生产状态。
- 资料中心：显示资源索引和文件元数据，不重复扫描同一文件。
- 收益中心：显示采集运行状态和已保存记录，停用账号不采集。
- 桌面小窗口：只显示摘要和异常任务，不建立第二套任务状态。

## 7. 验收标准

1. 打开生产中心后，不点击任何卡片，左侧数字和状态就是最新有效值。
2. 打开过的剧集再次进入时立即显示，并在后台自动校正。
3. 任务运行、完成、失败、超时或重试后，生产中心、任务中心和小窗口最终显示一致。
4. 切换页面不重复读取所有详情。
5. 本地服务短暂不可用时，页面不清空、不伪造 0、不把缓存当成永久事实。
6. 软件重启后，未完成任务、执行器暂停状态和历史错误仍可恢复。
7. 自动测试、Windows 桌面运行和剪映真实验收分别记录，不能互相替代。

## 8. 实施顺序

1. 统一后端摘要字段和状态映射；
2. 让生产中心和任务中心只使用统一摘要；
3. 修复详情缓存的后台校验和失效规则；
4. 增加任务变化通知或轻量增量刷新；
5. 接入资料中心、收益中心和桌面小窗口；
6. 进行重启、休眠、服务断开和真实 Windows 操作验收。

## 9. 青柠收益视频明细

1. 明细事实的唯一键是：数据日期 + 账号 + 平台视频 ID。同一天再次采集同一条视频时，更新该条记录，不重复增加一条。
2. 不同日期保留为独立日记录，才能查看同一视频在不同日期的播放和收益变化。
3. 收益中心按用户当前选定的日期范围读取明细；不得为了显示一个页面把所有历史视频明细一次传给前端。
4. 平台返回的剧名无法对应本系统剧集时，必须显示“待匹配剧集”，不能猜测或强行归入其他剧集。
5. “已匹配剧集”只表示剧名匹配；它不等同于已经关联到内部成片或素材。成片/素材归因要有单独的人工或自动核对记录后才能显示已关联。
6. 采集尝试日志和业务明细是两类数据：前者用于排错，后者用于分析。日志的保留期清理不能删除收益明细或日收益汇总。
7. 青柠明细的“首次观测日期”是本系统最早采到该平台视频的日期，可与账号、剧名一起推测候选生产任务；它不是平台直接返回的发布时间。
8. 推测命中生产任务后，只能列出该任务下的候选原素材供人工预览。人工确认后，才建立平台视频到具体成片/原素材的正式关联；关联结果按账号 + 平台视频 ID 保存，并复用于该视频后续各日收益。

## 10. 当前实现评估（2026-08-31）

本节用于区分“已经做到”和“还没有做到”，避免以后把局部改进误报成全部完成。

### 10.1 已经做到

- 页面首次打开可以先显示内存或本地缓存，再在后台检查最新摘要。
- 页面切换回来不会主动清空已经显示的内容。
- 生产中心、任务中心、资料中心和收益中心已经有基本的模块范围判断，不会因为一个收益操作就刷新所有页面。
- 本地服务暂时不可用时，页面原则上保留最后一次有效数据，不用空白或 0 覆盖真实数据。
- 生产中心列表使用摘要，打开剧集后才读取该剧集详情。
- 收益中心的总览和视频明细已经分开，视频明细不是总览页面必需的数据。
- 后端会为生产任务、素材、模板、成片、导出和执行器状态写入轻量变化记录；后台执行器的变化与用户点击操作使用同一通道。
- 生产中心按生产任务编号只更新对应账号 × 剧集的摘要和当前详情。
- 任务中心及顶部小窗口按生产任务编号只替换对应业务卡片；常规高频全量刷新已改为低频兜底检查。
- 资料中心的账号、剧集和生产资源变化按各自对象或资源列表更新，不再因其变化重读整套资料中心种子数据。
- 收益采集只在本次采集结束或失败后通知收益中心；收益中心只更新用户当前选择的日期范围，不在采集进度过程中反复重读数据。

### 10.2 还没有做到

- 收益中心进入详细页面时，仍可能读取较大范围的视频明细。
- 任务中心的服务端单任务接口目前复用现有卡片合并规则；后续可继续下沉 SQL 查询，减少服务端内部的无关记录计算。

因此，当前状态应表述为：

> **缓存优先、模块级刷新、生产中心/任务中心按生产任务刷新，以及资料/收益中心按其最小可用数据范围刷新已完成；服务端任务卡合并查询和收益明细的更细分段仍可继续优化。**

## 11. 目标改造方案

### 11.1 统一的数据更新通道

所有页面共用一个前端数据缓存层。页面只读取自己需要的数据，不能各自创建一套互相不了解的刷新逻辑。

每次后端数据变化都发送标准变化消息，至少包含：

- `change_type`：变化类型，例如任务状态变化、素材扫描、导出完成、发布登记；
- `account_id`：账号编号；
- `drama_id` 或 `production_task_id`：剧集或账号 × 剧集任务编号；
- `task_id`、`video_id` 或 `material_id`：更具体的对象编号；
- `updated_at`：变化发生时间。

没有对象编号的旧接口只能作为兜底全量刷新，不能作为长期方案。

### 11.2 四层数据读取方式

以后每类数据按四层处理：

1. **页面缓存**：用于立即显示上一次有效内容。
2. **列表摘要**：用于生产中心左侧、任务中心列表和小窗口，只返回列表所需数字和状态。
3. **单项详情**：只读取当前打开的账号、剧集、任务或视频。
4. **历史明细**：只有用户明确打开收益明细、采集记录或文件列表时才读取，并带日期、账号、剧集等筛选条件。

页面切换只检查摘要；打开详情只检查当前对象；后台任务变化只更新相关对象。

### 11.3 各模块的精准刷新规则

#### 生产中心

- 任务 A 的素材扫描完成，只更新任务 A 的左侧摘要和已打开的任务 A 详情。
- 任务 A 的模板或成片状态变化，不重新读取其他剧集。
- 当前没有打开详情时，不读取任何剧集的完整素材列表。

#### 任务中心和顶部小窗口

- 只更新变化的任务卡和对应执行器状态。
- 执行器当前任务变化时，只更新该执行器，不重建所有卡片。
- 异常数量可以由缓存中的任务状态增量计算，但必须以后台返回的任务状态为准。

#### 资料中心

- 修改账号只更新该账号。
- 修改剧场或子剧场时，只更新受影响的关联字段。
- 单个资源文件变化时，只更新该资源索引，不重新扫描全部资源目录。

#### 收益中心

- 采集完成后只更新本次采集涉及的日期、剧场和账号。
- 切换日期范围只读取新范围，不清空旧范围直到新结果成功返回。
- 视频明细按日期和账号分段读取，不把全部历史明细一次交给页面。

### 11.4 刷新触发顺序

一次用户操作完成后，按以下顺序处理：

1. 后端先完成数据库和文件事实写入。
2. 后端返回本次操作涉及的对象和最新状态。
3. 前端立即用返回结果更新当前页面对应对象。
4. 前端发送或接收变化消息，通知其他真正受影响的页面。
5. 其他页面只请求自己的摘要或单项对象。
6. 定时刷新只负责补救漏掉的消息，不负责每次都重读全部数据。

## 12. 刷新频率和并发规则

- 有任务正在执行：只对正在变化的任务做短间隔检查。
- 没有任务执行：摘要低频检查即可。
- 页面隐藏：停止普通刷新；页面恢复时补查一次摘要。
- 同一接口已有请求在进行：后续请求复用前一个请求，不重复发起。
- 同一对象的旧响应晚于新响应返回时，旧响应不得覆盖新数据。
- 用户主动点击刷新可以请求最新摘要，但仍不能清空页面等待结果。

## 13. 施工顺序

按以下顺序改造，不能跳过验收：

1. 统一变化消息格式，并补齐账号、剧集、任务、视频和素材编号。
2. 生产中心按 `production_task_id` 更新单个任务摘要。
3. 任务中心和顶部小窗口按 `task_id` 更新单项任务及执行器。
4. 资料中心按账号、剧集和资源编号更新单项数据。
5. 收益中心按日期、账号和剧集更新对应数据，减少大范围视频明细读取。
6. 将各页面重复的计时器收拢到统一缓存层。
7. 做 Windows 重启、页面切换、任务执行、失败恢复和服务短暂断开验收。

## 14. 每次施工的验收清单

每次修改刷新逻辑后，必须回答以下问题：

- 打开页面时是否先看到上一次有效内容？
- 新数据回来前是否保持旧内容，不出现空白或伪造 0？
- 修改一个对象时，是否只更新该对象？
- 无关页面和无关任务是否保持不动？
- 页面切换回来是否复用已有内容，而不是重新读取全部详情？
- 服务失败后恢复，是否能自动校正而不丢数据？
- 重启软件后，缓存是否只是临时显示，最终是否回到数据库真实状态？
- 任务中心、生产中心、收益中心和小窗口是否最终显示同一个后端事实？

自动测试、前端构建、Windows 桌面运行和剪映真实操作必须分别记录，不能用其中一项代替其他验收。

## 15. 明确禁止的做法

- 页面一打开就读取所有剧集详情、所有视频明细和所有资源文件。
- 任意一个接口操作成功后，让所有页面同时重新加载。
- 请求开始时先把旧数据清空，再等待新数据。
- 用界面按钮、前端计时器或 Mock 数据猜测后端任务状态。
- 用高频全量轮询代替变化通知和单项查询。
- 为解决一个页面的速度问题，复制出另一套数据库或另一套状态来源。
