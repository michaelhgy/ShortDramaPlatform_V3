# 试点方案 A：修复 2 个测试的隔离缺陷

> 状态：**已执行**（2026-09-17 用户批准后执行，提交见 `docs/决策日志.md`）。
> 验收结果：一键验证 **144 通过 / 0 失败**，前端类型检查通过，生产库 `v2_system.db` 修改时间未变。
> 三条验收标准全部达成；证据等级 **2（测试通过）**，不代表任何生产功能被验证。

## 为什么要做这个

1. 这是当前验证基线里唯一的噪声。修好之后，**任何新失败都等于真回归**，安全网才真正可信。
2. 现在这 2 个失败的测试会去连"环境里的数据库"——**如果哪天环境恰好可写，它们会把建表语句写进生产库**（2026-09-17 已发生过一次误碰）。修好等于堵住这个隐患。

## 根因（已确认，证据明确）

- `server/tests/test_v2_file_service.py` 第 17-24 行：

  ```python
  def setUp(self):
      self.temp = tempfile.TemporaryDirectory()
      root = Path(self.temp.name)
      service.WORKSPACE = root / "workspace"      # ← 直接改模块全局
      service.DATA_ROOT = root / "system-data"    # ← 直接改模块全局

  def tearDown(self):
      self.temp.cleanup()                          # ← 只删目录，没恢复全局
  ```

- 该测试类跑完后，模块全局 `WORKSPACE` / `DATA_ROOT` / `DATABASE_INITIALIZED_PATH` **仍指向已被删除的临时目录**。
- 后面的 `server/tests/test_v2_task_center.py` 中，`V2TaskCenterExecutorOwnershipTests` 的 2 个测试调用 `_executor_snapshot()` → `service.get_v2_settings()` → `connection()`。此时 `db_path()` 解析出的路径与 `DATABASE_INITIALIZED_PATH` 相同，于是走"快速路径"：

  ```python
  conn = sqlite3.connect(path, timeout=30.0)   # v2_file_service.py:737
  ```
  该路径**不做 mkdir**（只有 `_initialize_connection()` 才建目录），而目录已被删 → `unable to open database file`。

- 验证过：单独看这两个测试的逻辑本身没问题（其余 142 个测试通过），失败纯属**测试间状态污染**。

## 改动方案

**改动只限测试文件，不碰任何生产代码、不改任何业务行为。**

### 改动 1（治本）：让泄漏的全局复位

`server/tests/test_v2_file_service.py`

- `setUp` 里先保存原值，再改成临时目录：

  ```python
  self._originals = (service.WORKSPACE, service.DATA_ROOT, service.DATABASE_INITIALIZED_PATH)
  ```
- `tearDown` 里恢复原值，再清理临时目录：

  ```python
  service.WORKSPACE, service.DATA_ROOT, service.DATABASE_INITIALIZED_PATH = self._originals
  self.temp.cleanup()
  ```

### 改动 2（防御）：让这 2 个测试自带隔离

`server/tests/test_v2_task_center.py` 的 `V2TaskCenterExecutorOwnershipTests`

- 加 `setUp`/`tearDown`：用 `tempfile.TemporaryDirectory()` 把 `service.WORKSPACE` / `service.DATA_ROOT` 指向临时目录，并在结束时复位（与改动 1 同样的写法）。
- 这样即使将来别的测试再泄漏，这 2 个测试也不受影响——**测试之间不再互相依赖执行顺序**。

### 明确不做的事

- 不改 `server/v2_file_service.py`（不为了让测试通过而动生产代码）。
- 不删除、不跳过（`skip`）任何测试。
- 不调整测试顺序、不加 `pytest-randomly` 之类的顺序控制。

## 验收标准

1. 双击 `tools\一键验证.bat`：后端 **144 通过 / 0 失败**，前端类型检查通过。
2. 生产数据库 `D:\短剧推广运营系统\系统数据\database\v2_system.db` 的**修改时间不变**（证明隔离有效）。
3. `git diff` 只包含 2 个测试文件，无生产代码改动。

## 风险与回滚

- **风险：低。** 只动测试的 setUp/tearDown；若改法不对，最坏情况是这 2 个测试仍失败（回到现状），不会影响软件功能。
- **回滚：** `git revert <本次提交>` 即可。改动前已有快照提交可依赖。
