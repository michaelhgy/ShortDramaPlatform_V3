## 四、时效需求（**建议值 + 依据；待用户确认**）

| 数据类 | **建议时效** | 依据 |
|---|---|---|
| **A 手填资料** | **打开页面读一次 + 自己改完立刻刷** | 全历史变更仅 ~90 条 → 几乎不变，**不值得为它做实时机制** |
| **B/C/D/E 生产数据** | **3~5 秒统一刷新** | 用户 2026-09-18 明确"**几秒内变就行**"；实测每天几十到几千条，量极小 |
| **F 收益** | **打开时读 + 采集结束后通知一次** | 全历史仅 14 条变更；本身就是定时采集 |
| **G 系统内部** | **不显示、不拉取** | 用户不需要看变更日志和执行轨迹 |
| **H 微信指数** | **仅采集运行时 2~5 秒，结束即停** | 现在是无条件 1.5 秒全量重载 |

> **❓ 待用户确认的就是这张表**：可以接受吗？哪一类要更快 / 可以更慢？

## 五、"用什么方式做"（**由上面的需求推出来，不是一刀切**）

| 数据类 | 方式 | 为什么 |
|---|---|---|
| **A** | 打开页面读一次；自己改完立即局部刷新 | 几乎不变，实时机制纯属浪费 |
| **B/C/D/E** | **一个统一数据层，每 3~5 秒把摘要整体拉一次，所有页面共用** | 数据小（106 个任务，全量 48ms 级）；用户接受"几秒"；**全量拉不会漏、不会跳号、不需要编号** |
| **F** | 打开时读；采集结束刷新一次 | 一天变几次 |
| **G** | 不拉 | 不显示 |
| **H** | 只在采集运行时短轮询 | 其余时间完全不动 |

### 关键结论

**现在的问题不是"机制不够先进"，而是"所有数据都被当成同一类处理"**：

- 手填资料（几乎不变）被塞进变更通知
- 收益（一天几次）也走同一套
- 系统内部日志（用户根本看不到）也走同一套
- **然后因为没有对象编号，所有页面只能整块重刷；为了兜底，又加了 60 秒全量刷新和 5 秒轮询**

→ **按类分开处理，绝大部分复杂度自然消失。**
