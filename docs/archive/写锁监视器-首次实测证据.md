## 3. 结论

### 3.1 头号嫌疑：`scan_task()` —— 已由实测坐实形状

三次现场里有**两次**直接看到 `scan_task` 停在 **`content_hash()`（全文件 md5/sha256）**，一次停在 **`probe_material → resolve_ffmpeg`**。
与静态审计（2026-09-18，`server/v2_file_service.py:3438-3484`）完全吻合：

```
循环第 1 条素材末尾 INSERT → 写事务打开
循环第 2..N 条素材：md5 + sha256（整文件读、无超时）+ ffprobe + ffmpeg 抽帧 + 再 ffprobe
循环结束才 commit
```

**素材越多/越大，写锁被占越久**（20 条 1GB 素材 ≈ 读 40GB）。这解释了：
- 为什么"扫描素材"之后其它写操作会变慢；
- 为什么当时看到"`-journal` 大小恒定、不推进也不提交"——事务开着，人却在读文件、跑子进程，**根本没在写数据库**。

**诚实边界**：监视器证明的是"**写锁连续 6 秒拿不到**" + "当时各线程在做什么"。同一份报告里 `record_executor_trace`、`_ensure_columns`、`queue_template_job` 的栈都停在**写库调用上**——那是"在等锁"的姿态，与"`scan_task` 持锁"互为印证。这是**强指向**，不是"直接测量到持有者"；要 100% 确证，可在 `scan_task` 内临时计数，或改成"逐条提交"后看是否还复现（预期不再复现）。

### 3.2 顺带抓到的第二个问题：任务中心每 0.5 秒抢一次写锁

`task_center_service.py:240 _loop()`（每 0.5 秒一轮）→ `dispatch_once:235` → `_claim_next_template_job:104` → `_executor_available:84` → `ExecutorManager.__init__` → `executor_management.py:37 _ensure_columns()` —— 这个函数**结尾无条件 `commit()`**。
→ **空闲状态下也会每 0.5 秒发起一次写库提交**（约 2 次/秒），永远在跟真正的写者抢锁。静态审计把它列为"潜在边界问题"，实测证明它**每次派发都走这条路径**。

### 3.3 影响面（对用户意味着什么）

- **读取不受影响**：WAL 已生效，界面不会因此读不出数据（这也是用户说"现在基本不卡了"的原因）。
- **写入会被推迟**：其它写操作最多等 `timeout=30` 秒；实测到的连续占锁约 6 秒。
- 也就是说：**这条 bug 现在表现为"偶尔慢一下"，不再表现为"界面读不出数据"。**

## 4. 该怎么修（与 `docs/待做需求清单.md` 第 8 项合并处理）

| # | 位置 | 修法方向 |
|---|---|---|
| 1 | `scan_task()`（`v2_file_service.py:3438-3484`） | **把哈希 / ffprobe / 抽帧挪到写事务之外**；最省事的等价做法是**按素材逐条提交**（一条素材一个短事务），不要攒到循环末尾 |
| 2 | `executor_management.py:37 _ensure_columns()` | **只在真的补了列时才 commit**；热路径（每 0.5 秒）不应产生写库动作 |
| 3 | （其余）`run_due_cleanup` / `requeue_finished_video` / `_debug_sink` | 见第 8 项清单，一并处理 |

> 这三条的修复**不建议单独做**：刷新大修（`docs/待做需求清单.md` 第 7 项）很可能重写这些路径，避免"改了又搬"。
> 若用户希望在刷新大修之前先缓解，**只做第 2 条**（改动最小、收益直接：去掉每秒 2 次的抢锁）。
