> **建立 2026-09-18。** 用户要求：**先摸清"现在软件的功能和结构"，再说"应该怎么做"**。

> 配套：`docs/数据与功能全景.md`（有哪些数据、多久变一次）、`docs/V2数据与刷新规则.md`（用户自定的目标规则）。

## 一、现在的软件结构

### 1.1 页面（用户实际看到的）

| 页面 | 干什么 | 数据从哪来 |
|---|---|---|
| **顶部状态条**（每个页面都有） | 账号数 + 生产任务摘要 + 昨日收益 + 资源数 | 4 个接口，`Header.tsx` |
| 工作台（首页） | ⚠️ **还没做**，示意数据 | 假数据（用户确认不用管） |
| **生产中心** | 任务卡片列表 + 打开某任务看素材/模板/成片 | `productionService.ts` |
| **任务中心**（浮层） | 三个执行器状态 + 任务卡 | `taskCenterService.ts` |
| **资料中心** | 资料 / 生产资源 / 爆款资产 | `assetsCenterService.ts` |
| **数据分析** | 收益 5 个子模块 + 微信指数 | `revenueAnalyticsService.ts` |
| 参数中心 / 设置 | 各种参数 | 直接调接口 |

### 1.2 数据是怎么流的（**现在的样子**）

```
  顶部状态条      生产中心      任务中心      资料中心      数据分析
      │              │             │             │             │
      └──────┬───────┴──────┬──────┴──────┬──────┴──────┬──────┘
             ↓              ↓             ↓             ↓
      productionService  taskCenter-  assetsCenter-  revenueAnalytics-
        （自己的缓存）     Service      Service        Service
                          （自己的缓存）（自己的缓存）  （自己的缓存）
             │              │             │             │
             └──────────────┴──────┬──────┴─────────────┘
                                   ↓
                             后端接口（8782）

        ┌───────────────────────────────────────────────┐
        │  变更通知三件套（横插进来的"第三套机制"）        │
        │  dataChangeFeed → dataChangeEvents →           │
        │  dataRefreshCoordinator                        │
        └───────────────────────────────────────────────┘
```

### 1.3 一眼可见的三个结构问题

1. **每个页面有自己的 service + 自己的缓存** —— 一共 **4 套**，互不了解
2. **上面还压着第三套机制**（变更通知三件套），和下面 4 套**互相打架**
3. 因为互不了解 → 只能靠**"60 秒把所有页面全量刷一遍"兜底**

### 1.4 现在的刷新频率（**全都不统一**，等级 1）

| 谁 | 多久刷一次 |
|---|---|
| 变更通知轮询 | 每 **1.5 秒** |
| 生产中心 · 打开的任务详情 | 每 **5 秒** |
| **所有已打开页面** | 每 **60 秒全量** |
| 微信指数 | 每 **1.5 秒全量重载** |
| 设置页 | **从不**（只读一次） |
| 资料中心 | 靠变更事件（**无防抖**） |

## 二、结构上的问题（一句话）

> **同一份数据，被四五个地方「各拿各的、各存各的、各刷各的」；上面还压着一套不完整的变更通知。**

后果就是用户遇到的那些现象：界面不更新、刷不及时、切来切去被重置、出错了没提示。

**根因不是"机制不够先进"，而是"没有统一的地方管数据"。**

---

## 三、应该怎么做（**2026-09-18 依据 `docs/软件结构全景.md` 校正**）

### 3.1 核心：把"各拿各的"合并成"一个地方统一拿"

```
   页面们（状态条 / 生产中心 / 任务中心 / 资料中心 / 数据分析）
                        │  只订阅，不自己拿
                        ↓
        ┌──────────────────────────────────────┐
        │        统一数据层（新建）              │
        │  · 一份缓存（所有页面共用同一份）      │
        │  · 一个定时器（3~5 秒拉一次）          │
        │  · 一套失败处理（保留旧数据 + 提示）   │
        │  · 一套"改完立即刷"                    │
        └──────────────────────────────────────┘
                        ↓
                   后端接口
```

**变更通知三件套 → 简化掉。** 不需要"谁变了"的精准推送，因为数据量小到可以整体重拉。

### 3.2 逐条对应结构上的 6 个问题（见 `docs/软件结构全景.md` §4）

| 结构问题 | 怎么做 |
|---|---|
| **1. 切页签=卸载重建，现在靠它当刷新手段** | **分两段**：短期**保留不动**；等统一层全接完、数据能自己更新之后，**再改成"切走藏起来"**（这样筛选/选中项不再丢） |
| **2. 统一机制只覆盖 5 个页面** | **8 个页面全部接进来**（补上顶栏、工作台、参数中心、设置页、微信指数） |
| **3. 5 套缓存 + 同一份数据重复拿** | **收成 1 套**；删掉 `productionService` 与组件重复的那一份 |
| **4. 8 套计时器** | **只留 1 个**（统一层的 3 秒）；"走秒"这类纯显示、不发请求的可以留 |
| **5. "看起来对其实是写死的"** | **清掉**：要么接真实状态、要么删掉 |
| **6. `settings_changed` 发了没人听** | 参数中心/设置页改成从统一层读写 |

### 3.3 按数据分时效（**不是一刀切**，依据 `docs/数据与功能全景.md`）

| 数据 | 怎么拿 | 为什么 |
|---|---|---|
| **生产数据**（任务/素材/模板/成片/导出） | 统一层每 **3~5 秒**拉一次 | 用户明确"几秒内变就行"；实测核心数据仅几千行 |
| **手填资料**（账号/剧集/剧场） | **打开页面读一次 + 自己改完立刻刷** | 全历史变更才 90 条，几乎不变 |
| **收益** | 打开时读 + 采集结束后刷一次 | 一天采集几次 |
| **系统内部**（变更日志/执行轨迹） | **不拿** | 用户看不到，也不该看到 |
| **微信指数** | 只在采集运行时短轮询 | 其余时间不动 |

### 3.3 必须一起改的四件事（否则还是"修一个坏一个"）

| # | 改什么 | 为什么必须一起改 |
|---|---|---|
| 1 | **写操作完成后立即刷一次**（不等定时） | 用户点了按钮，界面必须马上反映 |
| 2 | **失败时保留旧数据 + 明确提示** | 现在大面积"出错装作没看见" |
| 3 | **筛选/选中项搬到页面外面** | 现在切页签组件被丢掉 → 全部重置 |
| 4 | **生产资源"录完就消失"要真落库** | 现在只写界面内存，**是真丢数据** |

### 3.4 做完之后"自然消失"的东西

60 秒无条件全量刷新 / 生产中心 5 秒轮询 / 微信指数 1.5 秒重载 /
各页面重复的缓存与防抖 / 游标跳号 / 抑制窗口吞事件。

**因为都不需要了。**

## 四、怎么落地（**每步都能停**）

| 步 | 做什么 | 验收（用户看得见的） | 能停吗 | 风险 |
|---|---|---|---|---|
| **0** | 给统一层装**报警器**（单测）——前端现在**零测试** | 故意改坏一处，测试必须变红 | ✅ 不影响任何东西 | 极低 |
| **1** | 建统一层，**先只接「生产中心」**，其他一律不动 | 列表/详情 **3 秒内自己更新**；切回来不闪不空白；断服务**有提示且不清空** | ✅ 其他页面照旧 | 中 |
| **2** | 接「顶栏 + 任务中心」（这三个共用同一份任务数据） | 三处进度一致；任一操作后另两处跟着变 | ✅ | 中 |
| **3** | 接「资料中心 + 数据分析」 | 改账号/剧集后资料中心自己更新；收益切时间范围**不串数据** | ✅ | 中 |
| **4** | 接「参数中心 + 设置页 + 微信指数」 | 参数改完，相关页面自己更新 | ✅ | 中 |
| **5** | **拆旧**：删掉各页面私有缓存 + 8 套计时器 → 只剩 1 套 | 行为不变，代码变少 | — | 中 |
| **6** | **页签改成"藏起来"**（**必须放在第 5 步之后**） | 切走再回来：筛选/选中项**还在** | — | 中 |
| **7** | 清理"写死的假状态" | "目录状态"能反映真实情况 | ✅ 可拆开 | 低 |
| **8** | 修那 11 条"实现坏了"的（删排期不落库等） | 逐条验 | ✅ 可拆开 | 低 |

> ⚠️ **不许跳步、不许一次全上。** 用户明确担心"修一个坏一个"。
> ⚠️ **第 6 步必须在第 5 步之后** —— 统一层没接完就改页签，会拿掉现在唯一的刷新手段。

### 4.1 这次不做的

- ❌ **工作台两版**（还没做的模块）
- ❌ **设置页那 4 个数据维护按钮 + 系统诊断**（还没实现的功能）
- ❌ 不改任何业务逻辑（怎么生成视频、怎么算收益）
- ❌ 不碰真实业务数据、不打包

### 4.2 最大风险

**现在软件是"能用但乱"，改刷新等于动所有页面的地基。** 所以：先补测试（第 0 步）、一次只接一个页面、每步都能退回去。

## 附录 A · 实测数据（证据等级 3）

| 测什么 | 结果 |
|---|---|
| 生产任务 | **106** |
| 31 张表全统计 | **19 毫秒** |
| 挨个检查 3,674 个文件路径 | **48 毫秒** |
| 数据库大小 | 33.84 MB |
| 变更事件 | 50,795 条（**77% 是 09-05 一次自激循环的残留**，现已不再发生） |
| 变更消息带对象编号比例 | `production_task_id` **19.1%**、`account_id` **0.0%**、`entity_id` **0.04%** |

**结论**：数据量小到**整体重拉完全可行**；"精准更新"在数据层面**根本做不到**（因为通知不带编号）。
