## 〇、全局诊断：这个软件是什么情况

### 0.1 规模（**等级 3，实测**）

| 维度 | 数量 | 说明 |
|---|---|---|
| 你在用的页面 | **8 个** | 工作台、生产中心、任务中心、资料中心、数据分析、参数中心、设置、顶部状态条 |
| 生产任务 | **106 个** | |
| 素材记录 | 1,230 条 | 其中磁盘上真实存在的只有 **59 条** |
| 成片任务 | 1,222 条 | |
| 账号 / 剧集 | 20 个 / 263 部 | |
| 数据库 | **33.84 MB** | 31 张表 |
| 前端代码 | 110 个文件 | |
| 全表统计耗时 | **19 毫秒** | 把 31 张表的行数数一遍 |
| 3,674 个文件路径挨个检查 | **48 毫秒** | |

**一句话定位**：这是**一个人用、数据在本地、规模很小的单机软件**。
数据小到「**把所有数据整体重新读一遍**」只要几十到几百毫秒 ——
**这一点决定了后面所有做法：不需要复杂的增量机制。**

### 0.2 软件里的东西分三类

#### 第一类：你要看的**数据**（8 类）

| 数据 | 多久变一次（等级 3 实测） | 现在怎么处理 | **应该怎么处理** |
|---|---|---|---|
| 账号 / 剧集 / 剧场等**手填资料** | 几乎不变（全历史加起来 **90 次**变更） | 塞进变更通知 | **打开页面读一次 + 你改完立刻刷** |
| **生产任务** | 每天几次 | 变更通知 | **统一数据层，3 秒一次** |
| **素材 / 模板 / 成片 / 导出** | 生成时集中变化 | 变更通知 | **统一数据层，3 秒一次** |
| **收益** | 一天几次（全历史 **14 次**变更） | 变更通知 | **打开时读 + 采集结束后刷一次** |
| **系统内部日志**（变更记录、执行器轨迹） | 持续 | 也进了变更通知 | **不显示、不读取** |
| 微信指数 | 采集时实时 | 自己 1.5 秒全量重载 | **只在采集运行时短轮询** |

> **这里是最关键的发现**：**这六类数据的需求完全不同，但现在被当成同一类处理** ——
> 全部塞进变更通知、全部靠「60 秒把所有页面整块重刷」兜底。
> **按类分开处理，绝大部分复杂度会自己消失。**

#### 第二类：你要做的**操作**（3 类）

| 操作 | 例子 | 要求 |
|---|---|---|
| **看数据** | 打开页面、切筛选、切页签 | 打开就有内容、不闪、不空白 |
| **改数据** | 扫描素材、生成模板/成片、提交导出、登记发布、改资料 | **点完立刻看到结果**（不等定时） |
| **后台跑** | 三个执行器、收益定时采集、文件清理 | 进度几秒更新一次 |

#### 第三类：**页面**（8 个）

| 页面 | 现在怎么刷新 | 谁跟它共用数据 |
|---|---|---|
| 顶部状态条（每页都有） | 变更通知 + 60 秒兜底 | 任务快照 **和任务中心、生产中心共用** |
| 生产中心 | 变更通知 + 60 秒兜底 + **自己 5 秒轮询** | 同上 |
| 任务中心 | 变更通知 + 60 秒兜底 | 同上 |
| 资料中心 | 变更通知 + 60 秒兜底 | 账号/剧集资料 |
| 数据分析 | 变更通知 + 60 秒兜底（微信指数**自己 1.5 秒**） | 收益 |
| 参数中心 | **从不**（只有手动按钮） | — |
| 设置页 | **从不**（只读一次） | — |
| 工作台（两版） | **从不**（示意数据，模块未完成） | — |

### 0.3 全局问题（一句话）

> **同一份数据，被四五个地方各拿各的、各存各的、各按不同节奏刷；
> 上面还压着一套不完整的变更通知。**

**具体表现**（都已在代码中定位，等级 1）：

1. **刷新节奏有 8 套**：1.5 秒（变更轮询）、5 秒（生产中心详情）、60 秒（全员全量）、
   1.5 秒（微信指数）、0.7 秒（采集进度）、1 秒（走秒）、50 毫秒（空转），外加两处「从不」。
2. **缓存有 5 套**，全部**没有过期时间**。
3. **变更通知约八成不带对象编号** —— 只说了"有东西变了"，没说是哪个 → 前端只能整块重刷。
4. **2.5 秒抑制窗口**会把真实的后台变更误当成"自己刚写完的回声"丢掉。
5. **大面积静默失败**（`catch(() => undefined)`）→ 服务出问题时界面一声不吭。
6. **「更新于 xx:xx」不可信** —— 不管成功失败都写当前时间。
7. **切页签 = 页面被整个拆掉重建** —— 这是现在最主要的"刷新手段"，也是筛选被重置的原因。

## 一、整体方案：一个数据层

### 1.1 目标形态

```
全部 8 个页面
      │  只订阅，不自己拿、不自己存、不自己定时间
      ▼
┌──────────────────────────────────────────────┐
│              统一数据层（新建）               │
│  · 一份缓存（现在 5 套 → 1 套，带"新鲜度"）   │
│  · 一个定时器 3 秒（现在 8 套 → 1 套）        │
│  · 一套失败处理：保留旧数据 + 明确提示        │
│  · 一套"改完立刻刷"                            │
└──────────────────────────────────────────────┘
      ▼
   后端接口
```

**变更通知那套依赖就此解除** —— 数据小到整体重拉完全可行，不需要"谁变了"的精准推送。

### 1.2 每一类东西分别怎么做

| 类别 | 做法 | 理由 |
|---|---|---|
| 手填资料 | 打开时读一次；你改完立刻刷自己 | 几乎不变，为它做实时机制是浪费 |
| 生产数据 | 数据层每 3 秒拉一次 | 你明确"几秒内变就行"；实测数据量极小 |
| 收益 | 打开时读 + 采集结束后刷 | 一天变几次 |
| 系统内部日志 | **不读** | 你不需要看变更日志和执行轨迹 |
| 微信指数 | 只在采集运行时短轮询 | 其余时间完全不动 |
| **改数据的操作** | 成功后**立刻刷一次**，不等定时 | 点了按钮必须马上有反馈 |
| **看数据的操作** | 先用缓存显示，后台校验，**失败不清空** | 不闪、不空白 |
| 切页签 | **改成"保留页面"**（筛选、选中项不再丢） | 数据由数据层保证新鲜，不需要靠重建 |

### 1.3 做完之后会"自然消失"的东西

60 秒全员全量 / 生产中心 5 秒轮询 / 微信指数 1.5 秒重载 / 8 套计时器 / 5 套缓存 /
游标跳号 / 抑制窗口吞事件 / "切来切去"当刷新。

**因为都不需要了。**

## 四、性能分析

### 4.1 实测数据（**等级 3**）

| 测什么 | 结果 |
|---|---|
| 31 张表全统计 | **19 毫秒** |
| 3,674 个文件路径挨个检查存在性 | **48 毫秒** |

**结论**：数据量小到「**整体重新读一遍**」完全可行，**不需要增量机制**。

### 4.2 请求次数的对比（**按代码里的间隔估算，等级 1**）

假设同时打开 4 个页面、持续 1 分钟：

| | 现在 | 改后 |
|---|---|---|
| 变更轮询 | 40 次 | **0**（不再需要） |
| 60 秒全员全量 | 4 个页面 × 5~10 个接口 = **20~40 次** | **0** |
| 生产中心 5 秒轮询 | 12 次 | **0** |
| 微信指数（若在采集） | 1.5 秒 × 4 个请求 = **160 次** | 只在采集时，且**合并为 1 次** |
| 统一数据层 | — | 3 秒 1 次 × 1~2 个接口 = **20~40 次** |
| **合计** | **约 230~250 次** | **约 20~40 次** |

**降低约 6~10 倍**，而且**节奏可预测**（现在不可预测）。

### 4.3 另一处真实的性能包袱（本次不修，但要记着）

那个被反复调用的"摘要"接口（`list_task_summaries`），
**内部会调用完整查询** —— 对每个任务再查 4~6 次数据库，还会做目录遍历和逐文件检查。
代码注释写着原因：**为了修"卡片和详情状态互相矛盾"**（典型的"修一个坏一个"）。
本次数据层会把它的调用**频率降下来**，但**接口本身的重活留到第 8 步**再说。

### 4.4 ⚠️ 用户的历史经验：**"以前最开始就是全量刷新，会很卡，页面经常闪"**

> 2026-09-18 用户口述。**这条推翻了"全量刷新没问题"的简单结论，必须写进方案。**

**关键区分：两个"全量"是不同的东西——**

| | 说明 | 代价 |
|---|---|---|
| **全量拿数据** | 从后端把所有任务数据拉一遍 | **很小**（106 个任务，实测几十毫秒） |
| **全量重画界面** | 把 106 张任务卡**全部重新画一遍** | **这才是"卡"和"闪"的来源** |

**以前的做法是两件都做了** → 所以卡。

**代码核实（等级 1）**：`ProductionCenter.tsx` 里 106 张任务卡是
`filteredUnits.map(...)` **内联渲染**的，**没有 `React.memo` 隔离**
（文件里只有 `useMemo`，那是缓存计算，**挡不住子节点重画**）。
→ **列表数据每换一次，所有卡片都会重画一遍。**

**因此方案加一条硬要求：**

> **全量拿数据，但只重画变了的那几条。**
> 做法：拿到新数据后**逐条对比**旧数据；**没变的沿用旧对象引用**
>（React 靠引用相等跳过重画），变了的才用新对象。
> 必要时再把卡片抽成独立组件 + `React.memo`。

**⚠️ 并记录一个差点犯的错**：第 1b 步把生产中心从「最坏 60 秒 / 靠切页签」
改成「每 3 秒」时，**没有同时做这个对比** → **重画频率提高约 20 倍**。
这正是用户担心的"修一个坏一个"。
→ **第 1b 步在用户实机确认"不卡不闪"之前，不算完成。**

## 五、需要你决策的（**只有 3 件，都能凭感觉判断**）

### 决策 1：数据多久刷新一次？

| 选项 | 效果 | 代价 |
|---|---|---|
| **3 秒**（推荐） | 干了活 3 秒内界面就变 | 后台每 3 秒发一次请求（实测数据量小，负担可忽略） |
| 5 秒 | 稍慢一点 | 更省 |
| 10 秒 | 明显要等 | 最省，但你会觉得迟钝 |

### 决策 2：数据读不到的时候，界面怎么表现？

| 选项 | 效果 |
|---|---|
| **显示上次的数据 + 明确提示**（推荐） | 不打断你干活；同时告诉你"这是旧数据" |
| 清空 + 报错 | 一眼看出出错了，但页面会变空，没法继续看 |

### 决策 3：切页签时，页面状态要不要保留？

| 选项 | 效果 |
|---|---|
| **保留**（推荐） | 切走再回来，筛选、选中的剧集还在。数据新鲜度由数据层保证，不靠重建 |
| 保持现在的"重建" | 切回来一定是最新的，但**筛选每次都要重选** |
