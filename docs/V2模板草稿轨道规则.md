# V2 模板草稿轨道规则

> 建立：2026-09-17。**依据真实运行验证**（用临时素材真跑 final 生成，检查产出的 `draft_content.json`），不是只看代码。
> 关联：`docs/术语对照表.md`、`docs/V2视频导出器设计.md`（导出环节）、`docs/V2生产文件迁移清单.md`

## 一、这层是干什么的

**模板草稿生成器**（代码在 `server/template_engine/`）负责把素材拼成一个剪映 5.9 能打开的草稿：

- **入料**：1 条竖屏真人视频 + 10 张 3:4 剧照 + 贴纸库 + 花字库
- **产出**：剪映草稿目录（核心文件 `draft_content.json`）
- **之后**：交给成片草稿生成器 → 视频导出器渲染成片

它**不启动剪映**，只写草稿文件。

## 二、正式模板的轨道结构（2026-09-17 实测）

| 轨道名 | 里面是什么 | 是否必须 |
|---|---|---|
| `T01_OUTER_VIDEO` | 中央真人视频窗口（矩形蒙版开窗，羽化固定 1） | 必须 |
| `T02_BOTTOM_PHOTO_WALL` | 底部人物照片墙（10 张剧照左右滚动，线性蒙版渐隐） | 必须 |
| `T03_TOP_PHOTO_WALL` | 顶部人物照片墙（同上） | 必须 |
| `T09_STICKER_SKIN_01` ~ `_16` | 16 条贴纸，全部来自**同一个皮肤** | 必须 |
| `T10_TEXT_BLESSING` | 祝福文案（花字样式） | **看文案池** |
| `T11_TEXT_DRAMA_PROMPT` | 引导文案（花字样式） | **看文案池** |

模板时长固定 **180 秒**。

### 已取消：T04 / T05（2026-09-17）

- **它们原来是什么**：上下两条**很窄的**（40–50px）、半透明、带**镜面蒙版**渐隐的**真人视频装饰带**，一条在上一条在下。
- **为什么取消**：用户判断作用不大，而且**每个模板都要额外准备 2 条真人视频**，太繁琐。
- **影响**：每个模板的真人视频需求 **从 3 条减到 1 条**。
- **代码处置**：`track04.py` / `track05.py` **保留归档、不删除**；诊断入口（`--stage t02-03` / `t04` / `t05`）仍能用它们做单轨调试，但正式 `final` 流程不再写入这两条轨道。
- **易混点**：照片墙（T02/T03，宽、剧照滚动）≠ 镜面视频带（T04/T05，窄、真人视频）。用户口语里的"轨道2、3真人视频"指的是**后者**。

## 三、文案配置规则（2026-09-17 新增）

**配置文件**：`D:\短剧推广运营系统\系统数据\模板文案.json`
（任务执行器自动把这个路径传给生成器；文件不存在时用内置默认池，行为与改动前完全一致）

**格式**：

```json
{
  "blessing": ["愿您身体健康", "愿您平安喜乐"],
  "drama_prompt": ["左下角免费看全集", "点免费剧集看全集"]
}
```

**三条硬规则（验收标准）**：

1. 字段**缺失** → 用内置默认池（向后兼容，不会因为漏写而丢轨）
2. 字段是**空数组 `[]`** → **不生成该条文案轨道**（草稿里必须不存在该轨）
3. 字段是**非数组**（如写成字符串）→ **明确报错**，不静默放行

**其他行为**：

- 生成时从池里**随机挑一句**（保留"每次不同"的感觉）
- 文案字数**不再限制**在 6–9 字：超出原档位时按**最接近的字数档位**取字号（改动前若填短文案会直接崩）
- 内置默认池在 `server/template_engine/jianying59_template/template_copy.py`（`DEFAULT_BLESSING_COPY` / `DEFAULT_DRAMA_PROMPT_COPY`，各 10 条）
- 读取逻辑同样在 `template_copy.py` 的 `load_template_copy()`

**举例**：想只要引导语、不要祝福语 →

```json
{ "blessing": [], "drama_prompt": ["左下角免费看全集"] }
```

## 四、剧照（照片墙素材）怎么选、怎么裁（2026-09-18 重做）

> 背景：用户 2026-09-18 报 `RuntimeError: T03/T04标准化后不是3:4：照片墙_3x4_03_xxxx.jpg`，
> 并指出"照片墙抽取的照片不太合适，我原本希望的是抽剧照图，从素材里面抽出人物图片"。

### 4.1 "不是3:4" 报错的根因（已修）

老代码用**四舍五入的浮点**凑 3:4：

```python
crop_height = round(width / (3 / 4))     # ← 会差 1 个像素
...
if normalized_width * 4 != normalized_height * 3:   # ← 要求精确，于是抛错
    raise RuntimeError(f"T03/T04标准化后不是3:4：{target.name}")
```

穷举实测：**9:16 竖屏常见尺寸 2360 种里有 1622 种（约 69%）会失败**。
例：源 136×241 → 裁成 136×181 → 比例 0.7513812 ≠ 3:4 → 报错。

**改法**：长边一律由**整数**推出（`height = width * 4 // 3`，必要时把宽往下退到能整除 3），
比例**必然精确**。另外补了两处隐患：

- `track02_03.normalize_three_four_photos` 的缓存从"文件存在就用"改成**先校验尺寸**，
  否则一个坏缓存会让任务**永远**以同一个文件名失败。
- 报错信息补上**源尺寸与结果尺寸**，下次一看就知道是谁。

### 4.2 选人策略（用户需求：要抽人物正面对镜头的）

**用户原话（2026-09-18）**："我的需求是从素材视频里面抽出 10 张人物图片拿来做照片墙，
图片当然是**人物正面对镜头**的那种比较好。"

| 项 | 做法 |
|---|---|
| 检测器 | **OpenCV 自带 `cv2.FaceDetectorYN`（YuNet）**，模型 232KB 随仓库与打包分发 |
| 为什么不用 mediapipe | 它要求**降级**本机 OpenCV（5.0 → 4.x），装不上也不值得；YuNet 零新增依赖 |
| 许可证 | MIT（`resources/YuNet-LICENSE.txt` 随附） |
| 检测方式 | 缩到 **640px 宽**检测，实测与全尺寸**同样准**、速度快一倍 |
| **正面判断** | **复用 YuNet 的 5 个关键点**（两眼、鼻尖、两嘴角）：鼻尖在两眼之间的相对位置 = 左右偏转，`0.5` 为正对镜头；再做俯仰。**不用装任何新库** |
| 挑图顺序 | **正面分 → 人脸质量 → 清晰度 → 明暗** |
| 裁切 | **以人脸为中心**（略偏上留头部空间）；没检测到脸则退回画面中心 |
| 取景下限 | 至少 540px 宽，避免裁出 200×270 这种会糊的小图 |
| 输出尺寸 | 统一缩到 **720px 宽以内**的精确 3:4 |

**关键点准确性怎么确认的（重要）**：把 5 个关键点**画在真实帧上**并排成图，
肉眼比对"yaw≈0.50 的一列是否都是正脸、yaw 4~21 的一列是否都是侧脸/低头" —— 核对通过才采用。
**没有只靠数字就相信指标。**

### 4.3 采样与门槛（都是实测定的，不是拍脑袋）

老做法：**按整批素材总时长均匀取 10 个时间点，每点看 ±2.4 秒**（共 50 张候选）。
在 2026-09-18 的真实素材上（1 部剧 12 集、合计 5066 秒）它会在第 8、10 集**恰好抓到没有人的片段**。

**实测基础数据**：480 张采样里，含可用人脸（人脸分 ≥0.5）的 **187 张 = 39%**；
而**含脸帧里只有约 14% 算得上"正对镜头"** —— 这才是真正的稀缺资源。

**参数怎么定的（密度扫描，2026-09-18）**：以"正面分 ≥0.75 且脸宽 ≥90px"为可用标准：

| 采样密度 | 候选数 | 可用帧 | 结论 |
|---|---|---|---|
| 24 窗 × 4 帧 | 96 | **7** | 凑不齐 10 张 ❌ |
| **24 窗 × 6 帧** | **144** | **14** | **选定** ✅ |
| 36 窗 × 6 帧 | 288 | 34 | 更宽裕，但取帧要 ≈40 秒，收益递减 |

**最终规则**：

1. 总时长切 **24 个窗口**，每窗取 **6 帧** = **144 张候选**；
2. 全部候选打分，**全局挑最好的 10 张**；
3. **正面分 <0.75 的不参与挑选**；
4. **脸宽 <90px 的不参与挑选**（实测会挑到 50~60px 的糊脸）；
5. 画面几乎相同的不重复用；**同一集最多 3 张**，且两张相隔 **≥8 秒**；
6. **门槛太严时逐级放宽**（`relaxed_frontal` → `relaxed_size` → `relaxed_all`），
   宁可挑到"没那么正"的脸也不让任务失败；放宽到哪一级会记进 `剧照准备清单.json` 的 `selection_stage`。

**性能（2026-09-18 实测，真实素材 12 集）**：
144 张候选（抽帧 + 人脸与关键点分析）约 **19 秒**，10 张 OCR 字幕处理约 **2.2 秒**，**整批约 21 秒**。
（上一版 96 张候选约 15 秒；多出的 6 秒换来"10 张全是正面"。）

**效果（等级 3 实测）**：

| 指标 | 第一版（无选人） | 第二版（选人，96 张候选） | **第三版（正面+门槛，144 张）** |
|---|---|---|---|
| 10 张里接近正面 | **2 张** | 7 张 | **10 张** |
| 正面分范围 | 最高 0.50 | 0.75~0.83 | **0.79~0.91** |
| 脸宽中位 | 155px（最小 50px） | 183px | **~270px（最小 141px）** |
| 精确 3:4 | 会报错 | 失败 0 张 | **失败 0 张** |

**已知局限（如实记录，未修）**：

- **同一位演员可能出现 2 张**。2026-09-18 已接入人脸识别（ArcFace）把上限压到 2 张，
  实测交付的 10 张里仍有 3 对相似度落在 0.53~0.87；其中 0.53/0.66 两对很可能是
  **长相相近的亲属**（该剧设定里有母女、兄弟）。
  用户 2026-09-18 明确："**这个影响不大的，只要不是一模一样的图片就行**" —— 因此不再收紧。
  **画面级去重（感知指纹）始终生效**，不会出现两张一模一样的图。
- **"眼睛看镜头"与"头转正"不完全等价**：本机测的是头部朝向 + 眼睑开合，不是视线方向。

**留证图片**（不用重新跑就能看）：

- `docs/images/photo-wall-compare/对比_老选图_vs_人脸选图.png`
  左列 = 老逻辑（只看清晰度、画面居中裁切）；右列 = 新逻辑（优先挑人脸、以人脸为中心裁切）。

### 4.4 三层漏斗：选图与"凑满 10 张"（2026-09-18 最终版）

**为什么要分层**：便宜的先筛，贵的只用在少数。全部候选都跑 AI 既慢又没必要。

```text
① 144 张候选 → OpenCV YuNet（31ms/张，零新增依赖）
     判：有没有人 · 脸多大 · 头转正没有（5 个关键点）
                ↓ 通过正面分与脸宽门槛
② 这些候选   → Google MediaPipe Face Landmarker（15ms/张）
     判：眼睛睁/闭（eyeBlink）· 嘴张多大（jawOpen）· 是否微笑（mouthSmile）
                ↓ 剔掉闭眼与夸张喊叫
③ 最终候选   → ArcFace w600k_mbf（16ms/张，走已有 onnxruntime）
     判：是不是同一位演员 → 同一位最多占 2 张
```

**工具与许可证（都是现成预训练模型，本项目只写"接起来"的部分）**：

| 用途 | 工具 | 模型 | 许可证 | 新增依赖 |
|---|---|---|---|---|
| 找人脸 + 头部朝向 | OpenCV **YuNet** | 0.23MB | MIT | 无 |
| 睁眼/闭眼、表情 | Google **MediaPipe Face Landmarker** | 3.6MB | Apache 2.0 | `mediapipe` + `absl-py` |
| 判定同一演员 | **ArcFace**（InsightFace 的 `w600k_mbf`） | 13.3MB | 按 InsightFace 许可使用 | **无**（复用已有 onnxruntime） |

**为什么不用 mediapipe 的默认依赖方式**：`mediapipe.tasks.python.vision` 会 import
`drawing_styles → drawing_utils → matplotlib.pyplot`（只为画关键点，我们用不到）。
为一行 import 装一个 matplotlib 不值当，所以 `drama_expression.py` 在导入前注册一个
**极小的占位模块**顶替它；实测完整的 landmark + blendshape 推断正常。
安装方式：`pip install --no-deps mediapipe` + `pip install absl-py`（`flatbuffers` 项目已有）。

**为什么不用 `insightface` 包**：实测它与"自己拼对齐 + 直接跑同一个 ONNX 模型"结果**等价**
（同一演员 0.69~1.00、不同演员 −0.19~0.36），而那个包会额外拉进
`onnx`、`scikit-image`、`scipy`、`matplotlib` 四个重依赖。

### 4.5 必须凑满 10 张（用户 2026-09-18 明确要求）

> 原话："照片墙如果不够 10 张，草稿可能会出问题，**宁愿说 10 张里面有些质量比较差，也不能少数量**。"

模板端三道硬校验（`track02_03.py`）：**恰好 10 个文件**、路径不重复、**SHA256 不重复**。
所以选图必须永远凑满，靠降级阶梯而不是报错：

| 档位 | 门槛 | 含义 |
|---|---|---|
| `strict` | 正面分≥0.75、脸宽≥90px、睁眼、不喊叫、同演员≤2、同集≤3 | 最好 |
| `relaxed_frontal` | 正面分≥0.55 | 好 |
| `relaxed_size` | 脸宽≥60px | 一般 |
| `relaxed_all` | 只要有人脸、画面各不相同 | 较差 |
| `duplicates` | 允许同演员反复出现，仍要求画面不同 | 差 |
| `variants` | 画面都不够时，对同一画面做**极轻微二次裁切**（偏移 1.2%）凑出不同字节 | 最差 |

**用了哪一档会写进 `剧照准备清单.json` 的 `selection_stage`**，并在任务日志里明确提示
"正面镜头不足，本次使用了「xxx」级别凑满 10 张"。

### 4.6 剧照缓存：按"账号+剧集"复用（2026-09-18）

- **单位 = 账号 + 剧集**。用户明确："账号a+剧集a 是一个模板，**账号b+剧集a 不能共用同一个**"。
- **位置**：`<系统数据>/剧照缓存/<账号__剧集>/<素材指纹>/`（新建目录，见文件生命周期规则）。
- **指纹** = 全部素材的「路径 + 大小 + 修改时间」。**素材一变指纹就变，自动重做**，不会用错图。
- **保留**：每个"账号+剧集"只留最近 **3** 份指纹缓存，更旧的自动删除。
- **实测**：同一单位第二次准备剧照 **25.3 秒 → 0.1 秒**。
- 缓存只是加速手段：写缓存失败**不影响**本次交付。

### 4.7 质量回报

`剧照准备清单.json` 的 `quality` 字段记录：`avg_frontal_score`、`min_face_width_px`、
`eyes_closed_photos`、`shouting_photos`、`smiling_photos`、`distinct_people`、`duplicate_fill_photos`。

**另一处顺带修复**：照片墙 OCR 字幕柔化以前是**硬依赖**——缺 RapidOCR 直接让模板任务失败。
现在改成"没有就跳过并记一笔"，换一台没装这个库的电脑不会因此挂掉。

## 五、怎么验证这一层（证据等级）

1. **等级 2**：`tools\一键验证.bat`（后端测试 + 前端类型检查）。
   - 文案：`server/tests/test_v2_template_copy.py`
   - 照片墙选人与精确 3:4：`server/tests/test_v2_photo_wall_faces.py`
2. **等级 3（真实素材，不改生产数据）**：
   - `py -3.12 tools\verify_photo_prep_real.py` → 真跑一次剧照准备，
     逐张打印尺寸/比例/人脸数/正面分/脸宽/闭眼度/微笑/演员序号，并输出成品拼图。
   - `py -3.12 tools\verify_delivered_identity.py` → 对**最终交付的 10 张图**再做一次身份核对
     （为什么不看清单：清单记的是候选帧的脸，必须用成品复核）。
   - 实跑一次 `final` 生成后读 `draft_content.json` 核对轨道名。
   - 2026-09-17 实测 3 个用例（默认 / 空文案 / 自定义）共 13 项断言全过。
   - 环境要求：`pyJianYingDraft`、`PIL`、`ffmpeg`；另外需要一个"剪映 User Data 的上级目录下存在 `Apps/*/Resources/Font/SystemFont/zh-hans.ttf`"，否则花字写入会报缺字体。
3. **只读诊断工具**：
   - `tools\probe_candidate_density.py` —— **改候选数量前必看**：多密的采样才够凑 10 张。
   - `tools\probe_photo_wall_thresholds.py` —— **改正面分/脸宽门槛前必看**。
   - `tools\probe_face_detection.py`、`tools\probe_face_coverage.py` —— 换机器/换素材后复测性能与覆盖率。
   - `tools\probe_face_pose.py` —— "正对镜头"的分布。
   - `tools\probe_expression_verify.py` —— 出图核对闭眼/张嘴指标是否判得准。
   - `tools\probe_face_identity.py` —— 人脸识别相似度分布。
   - `tools\compare_photo_wall_crop.py` —— 老选图 vs 新选图并排对比图。

> **写诊断脚本的纪律（2026-09-18 踩过两次）**：
> ① 诊断必须**调用真实流程的函数**，不要自己复刻取数逻辑，否则结论会和真实运行相反；
> ② 造测试/样本数据时，画面指纹、身份向量这类"必须互不相同"的字段要**真的互不相同**
>    （我曾在测试里用 `seed % 4` 造身份，导致 8 个人实际只有 4 个，白查了半天）。

## 六、边界与未做

- **照片墙仍只做"人脸"**：不检测全身/动物/多人关系。短剧里有动物的镜头可能被判为"没人"，
  此时退回按画面中心裁切（**不会失败**，也不会乱猜）。
- **模型缺失时不会失败**：读不到模型就退化成"按画面中心裁切 + 老的质量打分"，
  并在 `剧照准备清单.json` 里记 `face_detector_available: false`。
