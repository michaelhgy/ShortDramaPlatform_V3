本节为当前规则；下方旧日期的命令与耗时仅作历史证据，不再默认临时编排。已交付版本为产品 **3.0.2 / 2026.11.04.1**，已有 `.3 → 2026.11.04.1` 和 `.2 → 2026.11.04.1` 两个轻量包。本次只优化工具，不重新发布或覆盖它们。

### 每次发布的最短路径

1. **只确认一次发布范围、目标版本和收件人的基础版本。** 不通过开发机安装登记推断收件人版本，不擅自增加其他旧版直达包。并行开发时选固定源码快照；快照必须包含本次优化后的工具、`tsconfig.release.json` 和可用依赖，不把新参数传给旧快照的脚本。确认无误后才传 `--scope-confirmed`，不得用该参数代替范围调查。
2. 使用固定入口 `packaging/release_v3.py`。先 `--plan-only` 看计划，此模式不构建、不复制、不写发布工作文件。实际发布需要已统一的版本配置、明确 `--base-version` 和本功能的定向 `--test`；更新机制和版本检查固定执行，前端测试/正式构建各执行一次。
3. 主程序仅构建一次，直接输出到项目唯一的 `packaging/releases/<目标版本>`，避免从快照再复制整套发布目录；小修改默认复用 PyInstaller 分析缓存。仍需收集固定素材并生成目标完整程序目录，**不表示完全免除素材校验/磁盘写入**。首次安装、依赖/固定资源改变仍走全量包；Python、依赖、打包定义改变或缓存不可信时加 `--clean-program-cache` 使用全新分析。
4. 同一目标的多个**明确要求的**基线，只重复差异打包及各基线实际升级检查。构建侧 `release_hash_cache.py` 根据文件身份、大小和时间戳复用已发布只读构建的 SHA256；缺失/损坏记录重算。**不适用于会主动篡改内容并还原元数据的目录**；怀疑目录被改动时换用新的缓存路径或不启用缓存。安装端完整文件校验不使用缓存、不削弱。
5. 每个基线用真实交付 EXE 对隔离副本更新：核对全部目标文件、未知用户文件保护、未变化文件不重写、重复更新保护、错版拒绝；同一目标的冻结程序运行检查只执行一次，复用凭据同时绑定整个目标文件清单。隔离副本不使用硬链接，避免程序写入污染基线。不启动业务队列，不接触正式业务库或安装登记。
6. 默认**不再重做与本次改动无关的媒体全量回归**。媒体逻辑变更才安排对应样片；功能已经有与本次完整输入一致的 PASS 凭据时可复用，不凭旧测试数量声称当前通过。前端有改动时仍需对应可观察界面验证，脚本通过不能代替用户验收。
7. 日志逐阶段写到工作目录，正常只报告阶段、耗时、交付位置和结论；失败只读取失败日志的必要尾部，禁止反复回读整段日志或为打包重新扫描全仓库。禁止为常规发布另写临时编排脚本或默认扩展测试范围。

### 固定命令（由 Codex 执行，无须用户记命令）

以下占位符须替换为本次确认的版本与定向测试文件，**不要拿已交付的 2026.11.04.1 重打**：

```powershell
python packaging/release_v3.py --base-version <明确基础发布号> --version <新目标发布号> --source-root <V3内固定源码目录> --plan-only
python packaging/release_v3.py --base-version <明确基础发布号> --version <新目标发布号> --source-root <V3内固定源码目录> --scope-confirmed --test <本功能测试文件>
```

第二个基线确有交付需要时重复 `--base-version`，不重建目标。`--existing-target` 仅复用新流程生成且完整输入指纹匹配的目标；旧版本元数据没有 `release_input_hashes` 时不得伪造凭据强行复用。

工作目录默认 `packaging/work/releases/<目标版本>`，有 `state.json`、`inputs.json` 和各阶段日志。`--resume` 只在参数、源码、执行工具、Python依赖身份均一致时复用通过阶段，并重新核对输出指纹；源码/参数变化须另选工作目录。验收失败使用新 attempt 子目录，保留失败证据。**主程序或更新包构建中断后，如果留下已存在的半成品输出，禁止自动覆盖或删除；先查失败日志，按明确授权处理该半成品后再恢复，或另定新发布号。** 并发锁残留必须先核对进程和工作记录，不能盲删锁。

高级功能凭据 `--feature-receipt` 的 JSON 必须含 `status: PASS`、非空 `scope`、`checks`、`input_hashes`；后者须与 `release_v3.inputs(源码目录)` 完全一致。默认优先直接传定向 `--test`，不额外建立凭据管理系统。输入指纹包含发布代码、界面、构建配置、说明文档及需求文件；固定资源仍由资源收集/更新兼容检查负责，不因代码凭据跳过。

### 发布残留的保留与清理

只读盘点入口：`python packaging/audit_release_storage.py --output <盘点报告.json>`，跳过符号链接及目录联接，不移动/删除。文件逻辑大小不是实际可释放空间，硬链接可能共用磁盘块。

- **必须保留：** 当前目标及仍支持升级基线的完整构建、对外交付包、固定源码和对应验收结论；缺少基线就无法可靠制作后续差异包。
- **优先审核清理候选：** 老版本 `build`、无用编译缓存、已完成验收的安装副本、错误版本测试副本。先确认无进程占用及恢复/证据依赖，再取得明确清理授权，列出精确绝对路径和验证方式；不整目录清空。
- **单独审核：** `local-test-output` / `artifacts` 混有源码快照、样片、日志、失败证据，不可统一叫“垃圾”；旧完整发布也不能按数量或年龄自动删除。
- 不在常规发布后自动复制新的整套安装副本或任意保留同一目标的重复完整构建；验收只保留本次必要副本，后续清理仍走明确授权。

**本轮验证边界：** 40项隔离自动检查、工具编译、定向类型检查和只读计划预检通过；未执行优化入口的整轮真实发布，增量构建的实际提速需下次新版本发布记录。不能承诺固定分钟数，也不能把本次流程测试当成真实安装验收。详见事项档案《2026-11-04-V3发布流程优化与历史文件盘点》。

## 操作者怎么用

首次安装用完整安装包。已经安装指定基础版本时，小修改可以使用轻量更新EXE：等当前任务结束，正常退出V3，双击更新程序，确认它识别出的安装位置，点击“开始更新”。更新成功后仍从原快捷方式启动。

轻量包无需另装Python、Node或剪映。程序优先读取当前用户的V3安装登记，未找到时提供默认位置，也可手动选择包含`ShortDramaPlatformV3.exe`的真实安装目录。不会强制关闭V3或启动业务队列。

每个包明确支持一个基础版本到一个目标版本，不支持任意旧版跨级更新。已经是目标版本时，核对程序文件后提示无需重复更新；其他版本、V2目录、缺文件或文件内容不符时拒绝覆盖，提示使用匹配更新包或完整安装包。连续更新按版本顺序进行；发布时也可为常见旧版另做直达包。

## 更新范围与保护

轻量包根据已发布的完整构建逐文件比较，只携带变化的主程序、标准库压缩文件、前端和说明文档，并按清单移除新版不再使用的旧界面文件。固定贴纸、特效、FFmpeg、Python运行组件等保持原安装。固定素材或运行依赖有变化时，构建器明确拒绝生成轻量包，改用完整安装包。

账号数据库、风景、真人图片、模板缓存、成片和其他业务目录不进入包，也不作为恢复对象。安装目录里不属于程序清单的文件保留。

更新前先校验包内容、产品身份、基础版本、全部基础程序文件、文件占用、剩余空间和程序进程；同目录并发更新被锁定。清单禁止越界路径、Windows保留路径、大小写冲突以及链接目录。没有任何远程自动下载、后台静默更新或远程代码获取。

## 失败和中断恢复

只备份这次会变更的文件，备份、待替换文件和处理记录位于安装目录`.v3-updates/<版本与编号>/`。全部备份及新文件校验通过后才开始替换。替换期间先移走旧启动程序，其他文件校验和版本登记完成后再放入新启动程序，避免从原快捷方式启动到混合状态。

普通失败自动恢复原程序；突然退出或断电后，再运行同一更新程序，会先恢复未完成的文件操作，再重新检查并更新。备份损坏、恢复文件位置变化、文件在中断后被外部修改时停止，保留备份和错误原因，不覆盖未知内容。备份不自动清理。

恢复机制仅恢复尚未完成更新时的程序文件，不提供用户使用新版后任意降级的功能，不回退业务数据库。发布前由开发者判断业务数据兼容性；含数据库结构迁移且不适合程序回退的版本继续使用完整包和相应迁移方案。

轻量更新会同步当前用户V3安装登记中的版本显示；使用便携目录时不新增安装登记。旧完整安装器的卸载清单不包含轻量包新增文件，卸载后新增界面文件、说明及恢复备份可能保留；不会把这些文件伪装成已完全清理。

## 开发与打包入口

先完成本次变更所需的源码检查，再以Windows CPython3.12.10运行以下命令。基础构建必须是已交付、已验收的完整程序目录，保留在`packaging/releases/<版本>/ShortDramaPlatformV3/`。

从新源码制作下一版轻量包，命令例如：

```text
python packaging/build_v3_update.py --base-version 2026.10.25.2 --version 2026.10.25.3
```

命令自动执行前端类型检查和正式构建，再调用既有程序冻结流程生成新版本程序目录；最后比较两个构建，只生成轻量更新EXE，不编译几GB的完整安装器。小更新仍需要程序编译和必要检查，不能承诺所有改动都只花几秒。

若两个已验收构建均已存在，直接生成更新包：

```text
python packaging/build_v3_update.py --base-version 2026.10.25.1 --version 2026.10.25.2 --existing-target
```

第二条命令会复用现有构建，不重新编译主程序。输出为`packaging/updates/<基础版本>_to_<目标版本>/交付/`，含更新EXE、适用版本、中文说明及SHA256；已有版本或更新目录不覆盖。

`build_v3.py`继续提供完整程序冻结，`v3_installer.iss`继续用于完整安装器。轻量包生成器在`packaging/build_v3_update.py`，更新事务在`tools/v3_update_core.py`，可双击界面及隔离验收入口在`tools/v3_update_app.py`。

## 验收要求

自动检查覆盖正常更新、增加/替换/移除文件、重复运行、旧版不匹配、数据保护、运行中阻止、校验失败、空间不足、并发、失败恢复和中断恢复。发布时在独立安装副本实际运行更新EXE，核对目标版本全部文件、未变化素材、安装登记和实际软件运行结果；源码检查与真实升级、用户验收分开记录。

首次交付实例为2026.10.25.1到2026.10.25.2，说明见[轻量更新事项](../../事项档案/2026-10-25-V3轻量更新包与发布流程.md)。首次目标程序仍是已发布的2026.10.25.2，不为更新工具另起一个没有业务改动的版本号。
