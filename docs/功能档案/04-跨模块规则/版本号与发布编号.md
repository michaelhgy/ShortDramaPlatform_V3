## 适用范围

本规则只适用于 `D:\ShortDramaPlatform_V3`。V2 已封存，V2 既有版本号、安装包和升级包保持历史原样，不因 V3 版本规划而重命名或回写。

## 统一使用两种编号

V3 同时保留产品版本和技术发布编号，两个编号用途不同，不互相替代。

| 编号 | 示例 | 用途 |
|---|---|---|
| 产品版本 `product_version` | `3.0.0` | 用户看到的版本、关于页面、产品说明和功能变更沟通 |
| 发布编号 `release_id` | `2026.11.02.1` | 完整安装包、轻量更新包、构建目录、升级基线和交付审计 |

产品名称仍为“短剧推广运营系统 V3”。`V3` 表示产品线，不代替产品版本号。

## 产品版本递增规则

- `3.0.0`：V3 第一套正式稳定基线。下一次正式收口时可以采用这一产品版本；此前已发布的日期版本只作为历史发布编号保留。
- `3.0.x`：修复问题、调整细节或修正已有规则，数据结构和主要使用方式保持兼容。
- `3.x.0`：增加完整的新功能组，同时保持既有数据和使用方式兼容。
- `4.0.0`：发生需要迁移或明显改变使用方式的重大变化。

版本递增依据是实际功能和兼容性变化，不依据会话数量、修改文件数量或单纯重新打包次数。

## 发布编号规则

发布编号继续使用四段数字：

```text
YYYY.MM.DD.N
```

其中 `N` 是同一日期内的发布序号，从 `1` 开始。它用于让更新工具准确判断基础版本和目标版本，例如：

```text
2026.10.30.1 -> 2026.11.02.1
```

历史上已经发布的 `2026.10.27.1`、`2026.10.29.1`、`2026.10.30.1` 不重命名、不重写历史文档。下一次实际交付时，应使用真实交付日期和当日序号，不能提前把规划编号当成已发布版本。

## 版本来源

2026-11-03已建立单一版本配置源：

```text
packaging/version.json
```

内容至少包括：

```json
{
  "product": "短剧推广运营系统",
  "line": "V3",
  "product_version": "3.0.0",
  "release_id": "2026.11.03.1",
  "channel": "stable"
}
```

构建脚本、安装器、升级包清单、前端关于页面、后端运行信息和发布文档都应从这个配置源读取，避免 `package.json`、PyInstaller、Inno Setup 和升级脚本各自维护一套版本号。

当前产品版本3.0.0、发布编号2026.11.03.1。build_v3.py默认读取统一配置；EXE的FileVersion保留发布编号、ProductVersion为产品版本，build-metadata.json同时保留version/release_id及product_version。前端设置页直接编入同一JSON；/api/v3/version在冻结程序读取安装目录元数据，源码读取统一JSON，不访问业务库。安装器版本定义packaging/version.iss由构建器生成。package.json及锁文件根版本同步为产品版本。升级工具仍以release_id/兼容version字段判定顺序和基础匹配，显示两种编号，不改历史构建。

## 更新包命名

完整安装包和轻量更新包应同时带出产品版本与发布编号，至少在交付说明中同时记录，例如：

```text
ShortDramaPlatform_V3_3.0.0_2026.11.02.1_Setup.exe
ShortDramaPlatform_V3_Update_3.0.0_2026.10.30.1_to_2026.11.02.1.exe
```

现有更新工具的基础版本和目标版本校验仍以 `release_id` 为准；产品版本用于用户识别和功能沟通。

## 会话协作要求

- 其他会话开发期间，不修改版本配置、构建脚本和安装器的默认版本，避免与并行开发互相覆盖。
- 一个开发批次完成并准备发布时，先确定 `product_version` 和 `release_id`，再统一更新构建、安装、更新和文档入口。
- 版本收口前不得把日期编号写成已发布结果；源码完成、隔离构建、安装运行和用户验收分别记录。
- V2 的版本号和发布历史只读参考，不得为了统一格式修改 V2。
