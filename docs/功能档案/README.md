# 功能档案（唯一入口）

> 建立：2026-09-19（用户拍板）。**这份是"某个功能是什么规矩"的唯一出处。**
> 最后核对：2026-09-19 ｜ 状态：🚧 建设中（规则已定，档案逐份建）

## 0. 这份东西解决什么问题

用户原话：**"希望我们做的每个功能都能有记录留档，而且还是系统性的归纳，好比说随便提一个功能，马上能找到这个功能的详细说明，不至于每次都要翻聊天记录或者我给你完整口述。"**

所以这里的目标只有一个：**随口说一个功能 → 几秒内翻到它的详细说明。**

## 1. 归档判断规则（新东西来了，照着走）

```
新东西来了（一个新功能 / 一条新规矩 / 一个决定 / 一个 bug）
        │
① 它是"时间性"的吗？（某次排查过程、某次进度、某个决定、某个待办）
        │── 是 ──▶ 去 `docs/决策日志.md` 或 `docs/待做需求清单.md`   ← 不进档案
        │
② 它有"自己的入口"吗？
   （界面上点得进去：页签 / 弹窗 / 面板；或者后台自己定时跑）
        │── 有 ──▶ 它就该有一份档案（没有才新建）
        │── 没有 ─▶ 写进它所属的那份档案的对应段落   ← 默认走这条
        │
③ 这条规矩是不是好几个部件都要遵守？
        │── 是 ──▶ 只在 `04-跨模块规则` 里写全，别处只放一行链接
```

**四条护栏**（防它重新变乱）：

| # | 规矩 | 治的病 |
|---|---|---|
| 1 | **默认追加，不默认新建。** 新信息先问"它属于哪个部件" | 文件数失控 |
| 2 | **总数上限 ~25 份。** 超了说明粒度切错，要合并，不是再多开几份 | 变成几百个 md |
| 3 | **一件事只写一处。** 别处只放链接（例：`见《清理系统》§3`） | "一件事 4 份各写一遍" |
| 4 | **时间性内容不进档案**（进度、排查过程、某次结论） | 档案退化成日志 |

**判断轴只有一条：按"软件的部件"分，不按"哪次干的活"分。**
部件的数量是有限且稳定的（页签、执行器、后台机制），"事情"是无限的。

## 3. 每份档案的固定结构（**5 段**，段号永远不变）

```markdown
# <功能名>
> 一句话：<这个功能是干什么的>
> **他会这么说**：<用户平时怎么称呼它、会蹦出哪些词>
> 最后核对：YYYY-MM-DD ｜ 状态：已整理 / 待补全

一、它做什么     ← 产出什么、在整条链路里的位置（业务视角，一句话能懂）
二、怎么用       ← 点哪里 → 看到什么（操作路径）
三、业务规则     ← 主体：正面陈述"什么情况下会怎样"（分小节）
四、可调参数     ← 在哪调 / 默认 / 可选值（表格）
五、改动须知     ← 给 AI 用的：要注意什么 / 代码入口 / 改完怎么验
```

**段号固定 = 你不用记文件放哪**：问"参数在哪调"永远翻第四段。

**第三段是主体**；第五段是"不动手时不用看、一动手必须看"的那段。

**第五段必须回答三件事**（用户 2026-09-19 原话："不需要说你去到处找和考古，然后又要我补充一堆信息，你才能明白我说什么、代码要怎么改，要是没说明白，还可能改错东西"）：

1. **改这里要注意什么**：哪两个地方必须**成对改**（只改一个会报错/静默失效）；参数从界面到生效经过哪几环；哪些文件**不在正式链路上、别顺手动**；同一个值在几处各写了一份。
2. **代码入口**：文件 + **关键函数名 / 常量名**（不写行号——行号会漂移，函数名不会）。
3. **改完怎么验**：先跑哪条命令；哪些必须**实机看**（单元测试测不出来的，比如画面）；
   首次实机跑通后**把命令与现场条件记下来当基线**。
4. 🆕 **改这个功能时积累的经验 —— 第五段是唯一"越用越厚"的段**（用户 2026-09-19 点明）：
   每动过一次这个功能（开发或修改），回来把"**这次学到的**"追加一条——踩过的坑、必须先做的一步、验证时才发现的事。
   目的就是用户说的：**"做完了肯定会积累一些经验……下次再修改的时候就不用从头摸一遍"**。
   其余四段相对稳定，只有这一段**鼓励不断变长**；它是把"经验"从对话里搬进档案的地方。
5. 🆕 **第五段只记规则，不记故事**（用户 2026-09-19：先问"会不会越来越臃肿"，随后明确"**只记规则，不是到处打补丁**"）：
   - **「改这里要注意什么」就是一列规则**，每条都能直接照做（"改 A 必须同时改 B"）。
     **禁止出现**：「已取消」「原来是什么」「还没做」「没有入口」「已知局限」「别搞混」「历史上曾经」。
   - **负面事实改成正面规则**：不写"提交后不允许重复点击"，写"提交后本次尝试即结束"。
   - **要写"没做 / 没验证"的** → 那是进度，去 `docs/待做需求清单.md`，**不进说明书**。
   - **需要 AI 提防的** → 写成动作：不写"这里没验证过"，写"动它之前先在真机跑通一条做成基线"。
   - **不留"经验栏"**：每次改完功能，把这次学到的**提炼成一条规则**加进编号清单；提炼完只留结论，不留日期和故事。
   - **有上限**：第五段 ≤60 行；某个坑被代码修掉之后，那条规则就**删掉**——让代码不再容易改错，比永远记着强。

新档案照抄 `_模板.md`。

## 4. 写作标准

> **这份说明书是"给我们两个看的"**（用户 2026-09-19）：**用户偶尔查，主要是我（AI）在动手前读**。
> 所以它必须同时满足两件事：**用户看得懂**（一、二、三段说人话），**AI 不用考古**（第五段说清改哪、牵动什么、怎么验）。

> **总原则（用户 2026-09-19 原话）**："应该是**精准的描述我们的业务规则**。功能说明等等信息，而不是啰嗦太多东西。
> 有点像记成了'**西红柿炒蛋（没有东坡肉）**'——不是把错误的信息特地去标注，而是应该把功能说明写清楚。"
>
> → **正面写"它是什么、什么情况下会怎样"；不要用"它不是什么、它还没做"来描述。**

1. **只写"现在是什么"**：规则、行为、边界、默认值。
   - ✅ "爆款素材不足 120 秒时不插中插"
   - ❌ "任务级开关界面还没做""这条与文档冲突（❓）""旧脚本未改"
2. **不写变更记录** —— git 就是变更记录，档案里不抄一遍。
3. **不写"已知问题 / 待办 / 疑问"** —— 那些是**时间性**的，去 `docs/待做需求清单.md` 或 `docs/决策日志.md`；
   档案里只保留**会影响使用的限制**，并且当成规则正面写。
4. **少标出处** —— 正文按"事实就是如此"写；要追溯代码集中放第五段。
   （**不标"谁定的"**：规则就是规则。要表达"这是刻意为之、别当 bug 改掉"，**靠规则的措辞**——
   "必须""只降级、不报错""宁可…也不…"。谁定的、什么时候定的 → `docs/决策日志.md`。）
5. **能一句说完的不要写三句**；同一件事只在**一处**说全，别处放链接。
6. **术语第一次出现要解释**；读者可能第一次看这个功能。
7. **要能"跳着读"** —— 读者通常带着**一个具体问题**来，不是从头读。
8. **文件名必须点明主题**（`成片生成器.md` ✅，`笔记3.md` ❌）。

## 5. 怎么加一份新档案

0. **先盘点，再动笔**（2026-09-19 用户发现我漏了这一步）。
   把"我们聊过的 + 我顺手 grep 到的"当材料写档案 = **残缺档案**（《成片生成器》第一版就只写了"插片"这一角，
   漏了原素材四项检测、爆款素材怎么选、BGM、排队优先级、输出落盘、失败重试、状态回写…）。
   **盘点 = ① 通读这个部件的代码入口，把功能点列成清单；② 收集现有文档里所有涉及它的段落**（在 `docs/文档索引.md` 里搜，不是只挑聊过的）。
   **盘点没做完，不写档案。**
1. 用第 1 节的**三步判断**确认它够格单独建档（有独立入口）。
2. 复制 `_模板.md` 改名，文件名 = 功能名。
3. 填满 5 段；**第五段必须能指到具体文件**。
4. 回到本文件第 2 节的表里，把它的状态改成 ✅ 并加链接。
5. 改完提交 git（同一提交里带上这份 README 的更新）。

> **建设方式：边做边记（用户 2026-09-19 拍板）**
> 用户原话："先把现有的文档给整理一遍，**写了多少就记多少**，然后没有的就等，**我们需要修改那个功能、或者需要用到的时候再来整理**，
> 就是类似**边做边记**，现在特地全部盘点一遍太浪费 token 了。"
>
> 所以每份档案有两种状态，顶部"状态"栏要如实写：
>
> - **已整理**：现有文档里已有的内容已经归拢进来（**不等于"这个功能全写完了"**）。
> - **待补全**：只归拢了一部分，剩下的**在"要改这个功能"或"要用到它"时**再读代码补写。
>
> **不要为了"写全"专门去盘点每个功能**（那是一次昂贵的全量考古）。档案随用随补。
> 唯一例外：**你正要动这个功能**时，必须先补全它——否则会照着半份说明改代码。
