## 采集中心完成与跳过判定（2026-11-05）

- 按账号实际绑定的采集器和当前查单配置判断，不按剧场名字或“任务曾运行/执行结束”判断。
- 按日来源：保存成功的日期（包括来源明确返回且已保存的0收益）继续跳过。正常无数据只表示当次查询为空：最近7天这类日期保留“暂无数据，待复查”，最短间隔1小时后允许重查；同日稍后和次日采集都会检查，兼容已有空结果记录。超过复查窗口保留原无数据证据，不补0、不据此认定最终收益为0。失败、待更新及未查日期继续保留缺口。连续7天空/零停止首次倒查的规则独立保留，不把近期待复查重新变成整段历史未补齐。
- 只有当前累计的来源：按当前已配置期间和本次采集日判断是否成功查询，不要求不存在的逐日查询。能查历史月份的来源：必须覆盖软件实际支持、已配置的期间，并保留中断首次补采的原月份起点。不能因为本月成功就漏掉仍需补查的上月，也不要求没有专用入口的月份。
- 预判读取生效的全部配置，包括来源收益期间、子诗上月链接是否启用；历史月份复用条件与执行、任务预估共用同一规则。已有成功的历史月份正确跳过，历史月份无数据不能永久封存；当前累计最短间隔1小时后可再次查询，包括当天累计已经查成功的情况。
- 界面显示“暂无数据，待复查”或“间隔未到，稍后复查”；空结果任务保留来源待更新，不再仅凭有查询记录显示昨日完成。复查窗口和间隔由软件内置采集器定义 `empty_recheck_days`、`recheck_interval_minutes` 分别覆盖，默认7天/60分钟；目前不新增前端配置项。
- 月累计首次取得的总额全部记实际查询当日；同日更新只增加差额，漏日增量记恢复查询当日，跨月另建基准。任务记录的金额显示本次新增入账，日收益表保存当天合计。
- 一轮执行结束后再次检查账号实际覆盖情况；尚缺日期/期间时任务项保留待继续，不仅凭请求循环结束就报完成。采集轮次结束状态与业务数据完整状态分开。

## 一、它做什么

一次采集 = 一个**批次**，批次下面按「账号 × 数据日期」拆成一条条读取单元：

| 剧场 | 读取口径 | 一次读到什么 |
|---|---|---|
| 青柠剧场 | 公开收益页面，按天分页查 | 当日总额 + 该日每条视频的播放与收益明细 |
| 顶好剧场 | 收益接口，按天查 | 该账号该日的总额 |
| 触摸剧场 | 公开查询页 | 该账号**累计**广告收益（一个数） |
| 花生剧场 | 公开表格查询 | 该账号**累计**收益合计（一个数） |

结果写入兼容日收益表和驾驶舱的 V3 日期收益底座，并追加采集日志；另保存累计快照、首次补采状态。青柠视频明细默认不保存，已有明细不删除；后端显式启用时仍可保存。

## 二、怎么用

1. **手动采**：数据分析 →「收益」页签 → 右上角「采集收益」→ 抽屉「收益与数据采集中心」→ 选范围（全部已接入 / 按剧场 / 按账号）→「同步昨日」或「历史补采」→ 选日期 → 发起采集 → 看进度条（成功 / 无结算数据 / 失败三个计数）。
2. **查采集记录**：同一个抽屉下半部分，按剧场、账号、数据日期、结果筛选；同一账号同一天的历史尝试只显示最新一条。
3. **设自动采集**：设置页 →「收益自动采集定时任务」→ 开关 + 时间点（可增删）。

## 三、业务规则

### 谁触发、采哪一天

- **手动**：正常入口传昨天；历史日期区间仍可显式传入，最晚只能到昨天。新入口默认启用首次自动补采，`initial_backfill=false` 仅用于明确的日期区间操作。
- **自动**：后台每 **15 秒**检查一次，到点采前一天，并补查最近7天已查但仍暂无数据/失败的已知日期；复查遵守最短间隔。
- 软件当天首次打开时，已过点而当天还没跑过的时间点**合并补采一次**；批次里记着这次覆盖了哪些时间点，重启也不会把同一时间点重复跑。
- 自动采集看到已有批次在排队或运行中时，**本次检查跳过**。手动入口重复发起则返回已有收益批次及 `reused=true`，不另开线程。

### 采谁：停用继续查收益，注销停止采集（2026-11-06）

- 按账号明确选择的采集器固定编号分派，不按剧场名称猜测；剧场可由用户新建、改名。除注销外的账号（包含停用）按所选剧场/账号范围处理。未配置账号明确返回待配置失败，金额为空，不请求外部平台、不写假零。
- 账号没填视频号 ID → 这条单元直接记失败（说明写「账号未填写视频号 ID」），不写收益。

### 日期

- 青柠端原生、顶好端原生、青柠绿泡泡**按天逐日读**（选 7 天就是 7 次读取）。
- 累计查询的日期归属是北京时间下的**实际采集日**，不使用传入区间的末日伪装为历史日收益。
- 显式历史区间最多 90 天（含首尾）；首次自动倒查每轮每账号最多新读 90 天，已成功日期复用缓存，不消耗新读额度；近期空结果到达最短间隔后可重新查询，历史空结果仍可作为倒查边界。达到上限仍没有连续 7 天明确空/零的账号保留未完成状态，下次继续。
- 首次补采有独立完成标志，保存倒查起点；有部分成功不代表首次完成。失败会打断空/零连续计数，有未解决失败时不能标记首次完成。青柠明确空记录只用于停止倒查，不向日收益表造 0。
- 支持按月查询的累计来源使用本月及前两月；已成功补采的历史月不每天重查，失败月可重试。不同月份分别计算，不跨月相减。跨月中断保留首次原月份；月结后补读上月最终累计，不把月中快照当最终值。
- 累计首次 100 元、下次 130 元，分别写采集日 100 元和 30 元；同日到达最短间隔可重读，只补新增，日汇总不会重复相加。多个月份首次补采时只合并本次新增金额到采集日。
- 累计下降、无效/负金额记失败，保留原收益与累计基线。来源未确认所属周期时不能猜测清零日期；触摸/花生目前标为 `cumulative_unknown`。
- 旧累计成功日志可以作为原金额基线续接；不自动重算或修复旧版本已经保存的历史收益。

### 唯一键：同一天重复采集是更新

| 数据 | 唯一键 | 重复采集时 |
|---|---|---|
| 日收益汇总 | 账号 + 数据日期 | 正常采集复用成功结果；显式重读时，按日来源更新当日值，累计来源只累计当日新增差额 |
| 青柠视频明细 | 数据日期 + 账号 + 平台视频 ID | 同一条视频**更新**播放、收益、排名 |
| 采集日志 | 每次读取追加一条 | 只增不改 |

**不同日期各自独立**：显式启用视频明细保存时，同一条视频在不同日期各留一行；当前默认不保存明细。

### 「无结算数据」「失败」「零收益」是三件事

| 结果 | 什么情况下 | 写不写日收益 |
|---|---|---|
| 成功 | 平台正常返回、数值校验通过 | 写（金额可以是 0.00） |
| 无结算数据 | 平台正常返回「该日没有收益记录」 | 不写 |
| 失败 | 网络、解析、校验不通过，或账号缺 ID | 不写 |

- 青柠写完一天前先**对账**：页面声明的记录数、总计金额必须与抓到的明细一致，对不上就整条判失败，**一个数都不写**。
- 顶好接口查询成功且明确返回0.00时，原站提示查询数据为空，记为**无收益记录**，参与连续7天停止判断；金额为空，不造日收益0，也不据此判断账号ID是否存在。接口报错、缺金额、异常格式仍失败。
- 零收益要平台明确给出 0.00 且校验通过，才算成功。

### 明细怎么对上剧集和成片

- 平台剧名匹配到本系统剧集 → 标「已匹配剧集」；匹配不上 → 标「待匹配剧集」，不猜、不强归。
- 平台视频与内部成片的关联在候选列表里**人工确认**；确认结果按「账号 + 平台视频 ID」保存，复用于该视频之后各天的收益。

### 日志、明细与批次状态

- **采集日志与业务明细是两类数据**：日志管排错，日收益与视频明细管分析；清日志**不碰**后两者（清理规则见《清理系统》）。
- 批次走 `queued → running → completed / failed`；跑的时候记当前剧场、当前账号与三个计数。首次倒查的总量是上限，结束时按实际读取数收口；批次完成不代表每个账号首次历史都已补齐，`error_message` 保留未补齐账号数，能力接口提供 `backfills` 明细。
- 采集期间软件重启，未跑完的批次记为失败，说明是「软件重启，未完成的收益采集已停止，请重新发起采集」；「采集记录」里最新一条日志的 id 当作「收益数据变了没有」的信号，编号一变收益页重新拉数据。

## 五、改动须知（动这个功能前先看这段）

1. **写库必须幂等**：日收益按「账号 + 数据日期」、明细按「数据日期 + 账号 + 平台视频 ID」做 upsert，任何新写入都要能重复执行而不多出行。
2. **采集器读的是公开网页**：站点改版会让解析失效，解析不到必须落成明确的**失败态**、金额留空；宁可整条判失败，也不把解析不到的数字记成 0。
3. **不动已存的历史明细**：重采只更新同键那条；加字段按《界面与开发规范》升 `SCHEMA_VERSION` 并写 `ALTER TABLE` 迁移。
4. **手动与自动共用一个执行体**：两条路都必须走 `start_revenue_collection()`——批次记录、进度计数、证据链都在它里面；另开一条采集路径会让日志和进度对不上。
5. **新增剧场集中接入**：在 `server/revenue_collectors.py` 的 `REVENUE_ADAPTERS` 登记稳定 `adapter_key`、显示名、别名及真实能力，添加对应抓取函数与 `_fetch()` 分派；同一剧场多个采集器可登记同组别名，名称匹配只用于人工确认建议；支持按月查询的累计来源注册到 `MONTHLY_FETCHERS`。采集与估量共用能力，不另建一套日期策略或任务框架。先验证正常、空数据、失败、分页和金额；没有实现的来源不进入软件采集器列表；未配置的账号明确返回失败。
6. **新平台的「真零收益」先定义再动手**：确认不了就记失败，禁止默认按 0 写。
7. **日志与明细分开清理**：清 `v2_revenue_collection_attempts` 的代码不许顺手删 `v2_daily_revenues` / `v2_revenue_video_details`。
