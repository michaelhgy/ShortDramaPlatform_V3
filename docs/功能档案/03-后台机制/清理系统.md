# 清理系统

> 软件自动把"用完的东西"删掉：发布满 24 小时删中间产物，满 7 天删原素材；另有一键清理和孤儿记录体检。
> **他会这么说**：「清理」「删剧集」「保留期」「24 小时」「7 天」「幽灵任务」「孤儿」
> 最后核对：2026-09-19 ｜ 状态：已整理

## 一、它做什么

两套**完全不同**的删东西机制，别混在一起看：

| | **A. 删除剧集**（你说删就删） | **B. 发布后清理**（到点自己删） |
|---|---|---|
| 谁触发 | 你在生产中心点"一键清理" | 后台**每 30 秒**自己检查一遍 |
| 删任务主表吗 | ✅ 删整行 | ❌ **不删**，登记信息永久保留 |
| 删磁盘 | 整个任务目录 | 24 小时后：模板 / 成片 / 缓存 / 剪映草稿；7 天后：原素材 |
| 能撤销吗 | 不能 | 不能（但登记信息还在） |

## 二、怎么用

1. **清理某部剧**：生产中心 → 卡片 → 一键清理 → **先给预览**（删什么、多大）→ 确认才真删。
2. **看有没有"幽灵任务"**：任务中心顶部——**有孤儿记录时才出现**橙色提醒条，可一键清除。
3. **改删除期限**：设置页 →「文件清理周期设置」。
4. **清已结算的明细**：目前只有接口（`GET/DELETE /api/v2/task-center/settled-records`），**界面上没有入口**。

## 三、业务规则

### 两个时间点，在**登记发布那一刻**就算好了

```
process_cleanup_at = 实际发布时间 + 24 小时   ← 到点删中间产物
raw_cleanup_at     = 实际发布时间 + 7 天      ← 到点删原素材
cleanup_status     = active
```

改设置页的期限，**只影响之后新登记的发布**——已经登记过的任务，时间是当时算好的。

### 状态怎么走

```
active ──(24 小时到)──▶ process_cleaned ──(7 天到)──▶ raw_cleaned   （终态）
   │                          │
   └─ 删失败 ─▶ partial        └─ 删失败 ─▶ raw_partial
                （下一轮自动重试，不会卡死）
```

### 删除剧集 = **连子表一起删**

删一部剧会同时删掉它名下的：导出尝试 → 导出任务 → 模板任务 → 成片任务 → 生产文件 → 预约 → 追踪记录。

### 一个文件被占用，不会拖住整批

删文件遇到"被占用"这类**可重试**的错误会退避重试 3 次；**仍失败只跳过该文件、继续删下一个**。

### 孤儿记录（"幽灵任务"）

- 什么叫孤儿：**子表记录还在、但它所属的任务已经被删了**——界面上会显示成「未知账号 ×《未知剧集》」。
- 体检：任务中心顶部的提醒条；命令行 `tools/cleanup_orphans.py`（**默认只预演，加 `--apply` 才真删**）。
- 清理**只删数据库行，磁盘文件一个都不动**。

### 变更事件只留最近 1,000 条

裁剪随 30 秒清理循环走，**节流 10 分钟**一次（不是每次都裁）。

### 已结算明细：只在"原素材也清完"时才列进清理名单

`process_cleaned` 阶段**保留明细**便于排查；**不删主表行**（发布登记 / 时间 / 地址 / 收益关联都在主表）。

## 四、可调参数

| 参数 | 在哪调 | 默认 | 范围 |
|---|---|---|---|
| 发布后短期清理（小时） | 设置页 →「文件清理周期设置」 | 24 | 1~168 |
| 原素材保留（天） | 同上 | 7 | 1~90 |

写死在代码里的：变更事件保留 1,000 条；文件删除重试 3 次；扫描间隔 30 秒。

## 五、改动须知（动这个功能前先看这段）

### 一句话：删东西必须"删干净"，改期限要分清"已发布 / 未发布"

1. **删父对象必须级联删子表**。历史上只删主表 → 留下 654 条孤儿 → 界面冒出 10 个「未知账号 ×《未知剧集》」分组。
   **任何"删除"类改动，都要先问：它名下还有哪几张表？**
2. **改保留期只改设置项，不要改已算好的时间戳**。已发布任务的 `process_cleanup_at` / `raw_cleanup_at`
   是发布时写死的快照；要让新期限生效，只能影响**之后**的发布。
3. **删文件必须走 `_remove_one()`**（带可重试错误识别 + 退避 + 单个失败不拖累整批），
   不要直接 `unlink` / `rmtree`——被剪映占用的文件会让整批中断。
4. **到期扫描必须走索引** `idx_production_tasks_cleanup_due`。改查询条件时别把索引废掉，
   否则又变成"每 30 秒全表捞一遍"。
5. **改触发器定义必须配 `DROP TRIGGER`**：安装用的是 `CREATE TRIGGER IF NOT EXISTS`，
   不先 DROP 的话改了定义**永远不会生效**（31 个触发器已改成幂等重建，新加的照做）。
6. ⚠️ **已知风险（09-18 静态审计，未复核是否仍成立）**：`run_due_cleanup()` 是长事务——
   先写库、再真删文件、**最后才提交**；异常导致 `last_cleanup` 不更新时会高频重进，并堵住任务中心派单。
   **动它之前先复核这一点。**
7. **改 DDL 必加 `SCHEMA_VERSION` +1**（见《界面与开发规范》）。

### 代码入口

| 干什么 | 文件 | 关键函数 / 常量 |
|---|---|---|
| 到期计算、状态机、扫描、删文件 | `server/v2_file_service.py` | `run_due_cleanup()`、`_remove_one()`、`_due_at_or_backfill()` |
| 发布登记时算两个到期时间 | 同上 | 登记发布接口里写 `process_cleanup_at` / `raw_cleanup_at` 的那段 |
| 孤儿体检 / 清除 | 同上 | `preview_orphan_records()`、`cleanup_orphan_records()` |
| 已结算明细体检 / 清除 | 同上 | `preview_settled_detail_records()`、`cleanup_settled_detail_records()` |
| 变更事件裁剪 | 同上 | `CHANGE_EVENT_RETENTION`、`_prune_change_events()` |
| 30 秒清理循环 + 裁剪节流 | `server/task_center_service.py` | `_loop()` |
| 命令行孤儿清理 | `tools/cleanup_orphans.py` | `--apply` 才真删 |

### 改完怎么验

1. **一定先跑**：`tools\一键验证.bat`（清理相关主要在 `server/tests/test_v2_file_service.py`）。
2. **必须实测的两条**：
   - 删一部剧后跑 `python tools\cleanup_orphans.py` 预演 → **应为 0 条孤儿**（级联删除生效）。
   - 发布后清理跑完，`GET /api/v2/task-center/settled-records` 的 `total` **应归零**。
3. 孤儿为 0 时，任务中心顶部的提醒条**不应该出现**。

### 改这个功能时积累的经验（**每次改完往这里加一条**）

- **2026-09-19**：删剧集原来只删主表一行 → 名下子表全变孤儿（实测 654 条）→ 界面出现「未知账号」。
  **结论：删任何父对象，先列出它名下的子表，一张都不能漏。**
- **2026-09-19**：31 个触发器用 `CREATE TRIGGER IF NOT EXISTS` 且从不 DROP →
  **改了触发器定义也永远不生效**。结论：改触发器 = DROP + CREATE，并升 `SCHEMA_VERSION`。
