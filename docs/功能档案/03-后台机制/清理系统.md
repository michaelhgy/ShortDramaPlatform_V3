# 清理系统

> 一句话：软件自动把"用完的东西"删掉——发布满 24 小时删中间产物，满 7 天删原素材；另外提供"一键清理"和孤儿记录体检。
> 最后核对：2026-09-19 ｜ 状态：✅ 在用

---

## 1. 这是什么（人话）

磁盘会被塞满，所以有两套删东西的机制，**它们完全不同、不要混为一谈**：

| | **A. 删除剧集**（你说删就删） | **B. 发布后清理**（到点自己删） |
|---|---|---|
| 谁触发 | 你在生产中心点"一键清理" | 后台**每 30 秒**自己检查一遍 |
| 删任务主表吗 | ✅ 删整行 | ❌ **不删**，永久保留登记信息 |
| 删磁盘 | 整个任务目录 | 24 小时后：模板/成片/缓存/剪映草稿；7 天后：原素材 |
| 能撤销吗 | 不能 | 不能（但登记信息还在） |

## 2. 怎么用（点哪里 → 看到什么 → 出什么结果）

| 你想干什么 | 在哪 | 会发生什么 |
|---|---|---|
| 清理某一部剧 | 生产中心 → 卡片 → 一键清理 | 先给**预览**（要删什么、多大），确认后才真删 |
| 看有没有"幽灵任务" | 任务中心顶部 | **有孤儿记录时才出现**橙色提醒条，可一键清除 |
| 改删除期限 | 设置页 →「文件清理周期设置」 | 改完下一个到期的任务按新期限走 |
| 清已结算的明细灰尘 | 接口 `GET/DELETE /api/v2/task-center/settled-records` | ⚠️ **只有接口，没有界面** |

## 3. 规则与逻辑（每条带出处）

### 3.1 发布后清理的两个时间点（登记发布时就算好）

发布登记的那一刻，后端直接算出两个到期时间写进任务行（`server/v2_file_service.py:3281-3283`）：

```
process_cleanup_at = 实际发布时间 + short_term_cleanup_hours   （默认 24 小时）
raw_cleanup_at     = 实际发布时间 + raw_material_retention_days（默认 7 天）
cleanup_status     = 'active'
```

- 默认值：`:2187-2188`（`raw_material_retention_days: 7`、`short_term_cleanup_hours: 24`）。
- 可调范围（`:2260-2262`）：**1~168 小时**、**1~90 天**，超范围会被拒绝。

### 3.2 状态机

```
active ──(24h 到)──▶ process_cleaned ──(7 天到)──▶ raw_cleaned   ← 终态
   │                        │
   └── 删失败 ──▶ partial     └── 删失败 ──▶ raw_partial
                 （下一轮重试，不会卡死）
```

### 3.3 每轮扫描：**走索引，不再全表算**

- 索引：`idx_production_tasks_cleanup_due(release_status, cleanup_status, process_cleanup_at, raw_cleanup_at)`
  （`v2_file_service.py:765`）。
- 扫描函数：`run_due_cleanup()`（`:3621`），查询条件在 `:3637-3638`——
  **只捞到点的（或时间戳空白的旧数据）**，不再每 30 秒把全部任务捞出来逐条算。
- 时间戳为空的老数据用 `_due_at_or_backfill()` 兜底（`:3643-3644`）。

### 3.4 删文件抗占用（一个被剪映占用的文件不能拖住整批）

- `_remove_one()`（`:3437`）：把**可重试**的错误（WinError 32/5/33、EACCES/EBUSY/EPERM）退避重试 3 次；
  **仍失败只记录该文件、继续删下一个**。

### 3.5 删除剧集 = **级联删除**（2026-09-19 修）

- 用户原话（2026-09-19）："现在是那个幽灵任务，看下这个数据是怎么来的。按理说，我现在是有任务清理的。"
- **老代码只删主表一行** → 名下子表全变孤儿（实测 10 个被删任务留下 **654 条**孤儿），
  任务中心显示成「**未知账号 ×《未知剧集》**」（19 组 = 9 真 + 10 幽灵）。
- **现在**：删主表 + 级联删 `export_attempts → export_jobs → template_jobs → production_video_tasks →
  production_files → 预约 → 追踪`；任务中心三处查询 `LEFT JOIN` 改为 `JOIN`（孤儿自动不出现）。
- 出处：`docs/待做需求清单.md` §12F（含完整实测数据）。

### 3.6 孤儿记录体检（有才显示）

- `preview_orphan_records()`（`:3692`）/ `cleanup_orphan_records()`（`:3725`）；
  接口 `GET/DELETE /api/v2/task-center/orphan-records`。
- 命令行版：`tools/cleanup_orphans.py`（**默认预演，加 `--apply` 才真删**）。
- 实测结果（2026-09-19 19:20）：孤儿 **0 条**，任务中心 **66 条 / 9 组**。

### 3.7 变更事件保留 **1,000 条**（不再是 5 万）

- `CHANGE_EVENT_RETENTION = 1_000`（`:60`）；裁剪函数 `_prune_change_events()`（`:217`），
  接进 30 秒清理循环并**节流 10 分钟**（不再只在服务启动时裁）。

### 3.8 已结算明细清除（只在 `raw_cleaned` 时列入）

- `preview_settled_detail_records()`（`:235`）/ `cleanup_settled_detail_records()`（`:258`）。
- **只在原素材也清完（`raw_cleaned`）时才列入**——`process_cleaned` 阶段保留明细便于排查；
  **不删主表行**（发布登记 / 时间 / 地址 / 收益关联都在主表）。
