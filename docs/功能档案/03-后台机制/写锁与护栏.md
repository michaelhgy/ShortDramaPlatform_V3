# 写锁与护栏

> 两道保险：软件同一时间只允许开一个窗口（两个窗口一起写会毁数据）；数据库写卡住时自动留下现场记录，下次一眼看出是谁在写。
> **他会这么说**：「双开」「只能开一个」「已经有一个在运行」「卡住」「database is locked」「写锁」「护栏」「监视器」
> 最后核对：2026-09-19 ｜ 状态：已整理

## 一、它做什么

装了两道**互相独立**的保险，都为了保护那份唯一的数据库（`v2_system.db`）：

| | **A. 单实例守卫**（挡住第二个窗口） | **B. 写锁监视器**（写卡住时留现场） |
|---|---|---|
| 什么时候动 | 软件启动、开始对外服务之前 | 软件整个运行期间，每 2 秒看一眼 |
| 平时表现 | 正常启动，什么都不说 | **一个字都不写**，日志不增长 |
| 触发时表现 | 拒绝启动，弹窗告诉你先关掉那个窗口 | 把"当时谁在写"写进日志文件 |
| 给谁看 | 你（大白话） | AI 排查用（线程在干什么 + 最后一条写库动作） |

数据库同一时间**只能有一个写手**。监视器的价值在于：卡住时能**指认是谁在写**，不用猜。

## 二、怎么用

1. **正常开始**：双击 `tools\start_v2_desktop.bat`（源码版）或 `ShortDramaPlatform.exe`（打包版）→ 窗口打开。
2. **它说已经有一个在运行**：按弹窗提示，**先关掉那个软件窗口**，再启动这一个。
3. **卡住时取证**：打开 `%LOCALAPPDATA%\ShortDramaPlatformV2\logs\write-lock-watchdog.log`，看最新一条报告。

源码版关闭窗口时，会结束本次启动的本地服务（8782）和前端开发服务（3000）；如果服务在启动源码版之前就已存在，则不会被源码版误结束。

## 三、业务规则

### 一个软件，一个实例

- 打包版和源码版**共用同一个数据库**。两个后端同时写，会互相破坏数据 —— 所以启动时就挡住，**宁可拒绝启动，也不允许两个一起写**。
- 判定方式：启动前**用"连一下试试"探测 127.0.0.1:8782**。连得上 = 已经有人在服务 = 拒绝启动。
  **必须用连接探测**：在这台系统上，直接"占端口"的探测**会假成功**，两个后端就会悄悄各写各的。
- 被拒绝时你看到的原话（源码版是控制台文字，打包版是弹窗）：
  「已经有一个「短剧推广运营系统 V2」在运行（本机 127.0.0.1:8782 已被占用）。请先关掉那个软件窗口，再启动这一个。」
  后面还跟着一句为什么：两个软件同时打开会同时读写同一份数据，可能导致界面卡住或数据出错，所以只允许开一个。

### 读取不受影响

- 数据库开着 **WAL**（写的时候读走自己的快照）：写被占住时，界面**照样能读出数据、照样快**。
- 写操作等不到锁时最多等 **30 秒**；等到了就继续，等不到才报错。写动作只是**被推迟**，不是丢失。

### 写锁监视器：只有连续占住才留证据

- 每 **2 秒**探一次写锁，每次最多等 **0.3 秒**；**连续 3 次**都拿不到才写一份报告
  → 也就是写锁**被连续占住约 7 秒以上**才留痕。
- 探测一旦成功，连续计数清零 → **正常的毫秒级写入不留任何痕迹**；写锁空闲时监视器**不产出任何输出**，
  它自己永远不会变成一个新的日志炸弹。
- 报告里有什么：发生时间、数据库路径、**最近一次数据库变更的类型（带中文说明）**、`-wal` / `-journal` 文件状态、
  以及**当时每个线程的调用栈**。
- **指认原理**：变更类型由数据库触发器写在**写者自己的事务里**，所以报告里那条"最近一次变更"
  就是"当时拿着写锁的人在干什么"（例：`material_changed` → 扫描素材；`video_export_changed` → 视频导出）。
- 变更类型到中文的对照表在 `server/runtime_guard.py` 的 `CHANGE_TYPE_LABELS`。
- 日志文件有上限：超过 **1 MB** 只保留尾部 **250 KB**。写日志失败绝不影响服务本身。

## 四、可调参数

| 参数 | 在哪调 | 默认 | 可选值 |
|---|---|---|---|
| 写锁监视器开关 | 环境变量 `V2_WRITE_LOCK_WATCHDOG` | 开 | `0` = 关；其它值 = 开 |
| 探测间隔（秒） | 环境变量 `V2_WRITE_LOCK_WATCHDOG_INTERVAL` | 2.0 | ≥ 0.05 |
| 连续几次算"被占住" | 环境变量 `V2_WRITE_LOCK_WATCHDOG_STRIKES` | 3 | ≥ 1 |

写死在代码里的：每次探测最多等 0.3 秒；日志上限 1 MB / 保留尾部 250 KB；写操作等锁超时 30 秒；服务端口 8782。

## 五、改动须知（动这个功能前先看这段）

### 一句话：改这里要注意什么

1. **写事务必须短**：不要在写事务里做全文件哈希、ffprobe / ffmpeg 抽帧、删大目录、调外部程序。
   这些慢活要么挪到写库**之前/之后**，要么**一条一提交**。写锁被占住的秒数 = 你事务里慢活的总时长。
2. **失败也要回滚**：写失败必须 `rollback`，用 `try/finally` 收尾，不要用 `except: pass` 把未提交事务留着
   —— 那条连接会一直握着写锁，后面所有写操作都在门外等。
3. **单实例判定必须用连接探测**（`port_is_in_use()`）：换成"直接占端口"的判定在本机**会假成功**，等于拆掉这道保险。
   端口号在**两个**入口各写了一份，改必须成对改。
4. **动护栏代码前，先在真实运行环境里跑一次**：这类代码只在真实并发和真实端口下才暴露问题，单测测不出来。
5. **加一种变更类型必须同时补 `CHANGE_TYPE_LABELS` 一行**：漏了，报告里就只剩英文类型名，指认照样成立但难读。
6. **监视器自身不能成为负担**：日志写法保持"有上限、失败不影响服务"，同时保住"连续才记、空闲零输出"。

### 改完怎么验

1. **一定先跑**：`py -3.12 tools\verify_v2.py`（或双击 `tools\一键验证.bat`）——后端必须全绿，
   护栏测试在 `server/tests/test_runtime_guard.py`（10 个：单实例判定 3 个 + 监视器 7 个）。
2. **必须实机看的**（单测测不出来）：
   - 同时启动两个实例 → 第二个**被明确拒绝**（退出码 1 + 那句人话），第一个**全程健康**（护栏不误伤正常启动）。
   - 写锁空闲时，日志文件**大小不变**（零输出）。
   - 故意占住写锁 → 日志里出现报告，并且含线程调用栈与"最近一次变更"。
   - 两条启动路径各走一次：源码版 `tools\start_v2_desktop.bat`、打包版 `ShortDramaPlatform.exe`
     （两者都走 `create_v2_server()`，端口判定与监视器都在那儿）。
3. **首次实机跑通后把基线记下来**：命令、当时做的操作、日志新增条数、退出码。
   建议基线：① 双击启动 → 正常进界面；② 再启一个实例 → 退出码 1 且提示含"只允许开一个"；
   ③ 写锁空闲 ≥ 1 分钟 → 日志文件零增长；④ 复现一次占锁 → 日志出现报告且末尾指向一个变更类型。
   复现步骤与结果数字**记一次就固定下来**，以后改动只比这几项。
