## 2026-09-17（性能故障修复：数据库结构脚本反复抢写锁）

### 现象（用户报告）
- 开启软件明显变慢；各页面刷新很久；**资料中心刷不出来并报错**。
- 用户补充：不是本次改动引起的，更早"改了启动方式"之后就出现。

### 根因（实测确认，证据等级 3）
- 接口实测：`/api/v2/settings` 首次 **12.8 ~ 30.6 秒**、`/api/v2/production-task-summaries` **42.5 秒**；同一时刻其他接口仅 **3 ~ 385 ms**。
- 外部直连库反复出现 `database is locked`；`v2_system.db-journal` 长时间存在。
- **`_initialize_connection()` 被反复调用**，每次都执行整套结构脚本（3 段 `executescript`：建表 + 16 个索引 + 37 个触发器 + 十几条 `ALTER TABLE`），**每次都要抢数据库最高级写锁**。库长期被写（前端 1.5 秒轮询 + 业务写），抢不到就等到 `sqlite3.connect(timeout=30.0)` 超时 → 表现为"启动慢 / 刷新卡 / 报 database is locked"。
- **修正初判**：DDL 本身并不慢——在 250MB 库副本上实测整套 DDL 仅 **76 ms**，真正的成本是**抢写锁的等待**。
- 结构核对：生产库与"标准结构"**完全一致**（131 个对象，零差异）→ 库结构早已最新，只是**从未被打上"已完成"标记**，于是每次白跑 DDL。

### 修复
- 新增 `SCHEMA_VERSION = 1`（`server/v2_file_service.py`），用 SQLite 自带的 `PRAGMA user_version` 作结构标记。
- `_initialize_connection()` 开头读版本号：**一致就直接返回**，不再执行任何 DDL。
- 原脚本末尾的"收益采集重启恢复"抽成 `_recover_interrupted_revenue_runs(conn)`，**快速路径也必须执行**（属业务逻辑，不可跳过）。

2. **防止复发**：新增 `CHANGE_EVENT_RETENTION = 50_000` 与 `_prune_change_events()`，服务启动时自动裁剪。
3. **首屏接口卡 29~37 秒**：`_recover_interrupted_revenue_runs` / `_prune_change_events` 改为**先读、没有实际工作就不写库**；并在 `main()` 里**预热连接**，把初始化放到开始接待请求之前。
4. **切换 WAL（最关键）**：`PRAGMA journal_mode = WAL`。实测：**故意占住写锁时，读取仍 1 ms 成功**。→ **用户已确认"刷新正常了"**。
5. **启动器不再狂起 PowerShell**：`_port_is_free()` 改用 socket 连接探测（原实现每次检查都启动一个 PowerShell，循环十几轮）。

### 仍未解决（下次接手从这里开始）

  下一步方法：逐个关停后台任务做对照实验（`start_scheduler` / `start_revenue_auto_scheduler` / `_resource_probe_loop`），**不要再靠猜**。

- **写锁监视器当天抓到 3 次**（13:42:12 / 13:49:24 / 13:51:24，全部发生在成片/导出正在跑的时段）。
