## 2026-09-17（性能故障修复：数据库结构脚本反复抢写锁）

### 现象（用户报告）
- 开启软件明显变慢；各页面刷新很久；**资料中心刷不出来并报错**。
- 用户补充：不是本次改动引起的，更早"改了启动方式"之后就出现。

### 根因（实测确认，证据等级 3）
- 接口实测：`/api/v2/settings` 首次 **12.8 ~ 30.6 秒**、`/api/v2/production-task-summaries` **42.5 秒**；同一时刻其他接口仅 **3 ~ 385 ms**。
- 外部直连库反复出现 `database is locked`；`v2_system.db-journal` 长时间存在。
- **`_initialize_connection()` 被反复调用**，每次都执行整套结构脚本（3 段 `executescript`：建表 + 16 个索引 + 37 个触发器 + 十几条 `ALTER TABLE`），**每次都要抢数据库最高级写锁**。库长期被写（前端 1.5 秒轮询 + 业务写），抢不到就等到 `sqlite3.connect(timeout=30.0)` 超时 → 表现为"启动慢 / 刷新卡 / 报 database is locked"。
- **修正初判**：DDL 本身并不慢——在 250MB 库副本上实测整套 DDL 仅 **76 ms**，真正的成本是**抢写锁的等待**。
- 结构核对：生产库与"标准结构"**完全一致**（131 个对象，零差异）→ 库结构早已最新，只是**从未被打上"已完成"标记**，于是每次白跑 DDL。

### 修复
- 新增 `SCHEMA_VERSION = 1`（`server/v2_file_service.py`），用 SQLite 自带的 `PRAGMA user_version` 作结构标记。
- `_initialize_connection()` 开头读版本号：**一致就直接返回**，不再执行任何 DDL。
- 原脚本末尾的"收益采集重启恢复"抽成 `_recover_interrupted_revenue_runs(conn)`，**快速路径也必须执行**（属业务逻辑，不可跳过）。

2. **防止复发**：新增 `CHANGE_EVENT_RETENTION = 50_000` 与 `_prune_change_events()`，服务启动时自动裁剪。
3. **首屏接口卡 29~37 秒**：`_recover_interrupted_revenue_runs` / `_prune_change_events` 改为**先读、没有实际工作就不写库**；并在 `main()` 里**预热连接**，把初始化放到开始接待请求之前。
4. **切换 WAL（最关键）**：`PRAGMA journal_mode = WAL`。实测：**故意占住写锁时，读取仍 1 ms 成功**。→ **用户已确认"刷新正常了"**。
5. **启动器不再狂起 PowerShell**：`_port_is_free()` 改用 socket 连接探测（原实现每次检查都启动一个 PowerShell，循环十几轮）。
6. **只重启后端、复用前端**：后端 8782 **总是重启**（开发时改 Python 代码必须重启才生效，这是该入口存在的意义）；Vite 3000 **刻意保留**（热更新已能反映前端改动，重启它要等冷编译——那正是"等一分钟"的主因）。

### 仍未解决（下次接手从这里开始）
- **那个"卡住的写事务"是谁开的，尚未定位**。WAL 已消除它对**读取**的破坏，但**写操作**仍可能被阻塞。
  下一步方法：逐个关停后台任务做对照实验（`start_scheduler` / `start_revenue_auto_scheduler` / `_resource_probe_loop`），**不要再靠猜**。
- `resource_index` 有 980 行，但磁盘上只有 266 个文件（714 行陈旧记录），待清理。
- "资源扫描竞态导致重复写库"（每次打开资源页面约 980 条日志）**仍未修**——这是日志暴涨的上游原因。

- **先测量，再猜原因。** 前两轮都是"看到慢就修一个可能的原因"，修了 4 处用户仍感觉"没变化"。

### 静态审计（子代理，证据等级 1）——"卡住的写事务"的代码级嫌疑清单
审计范围 `server/`（排除 tests）+ `tools/` 后端入口，结论：**至少 5 处「DML 之后、commit 之前」夹着分钟级文件操作**。按可疑度：

1. **`run_due_cleanup` + 调度循环**（`v2_file_service.py:3179` 配 `task_center_service.py:238-248`）——唯一**无人操作、每 30 秒自动跑**的一条：`_due_at_or_backfill` 先 `UPDATE`(3078) 开写事务，随后 `_remove_paths` 真删模板/成片/缓存/剪映草稿/源视频，直到 3216 才 commit。
   **放大器**：`last_cleanup` 只在成功返回后更新（245），一旦抛异常就变成**每 0.5 秒重进一次这个大事务**，同时把同一线程的 `dispatch_once()` 堵死 → 任务中心停止派发。
2. **`scan_task`**（`v2_file_service.py:3424`，关键 3438-3484）——**单次持锁最长**：写事务里对每条素材做 md5+sha256（全文件读、无超时）+ ffprobe(≤8s) + ffmpeg 抽帧(≤15s) + 再一次 ffprobe，唯一 commit 在 3484。
3. **`requeue_finished_video`**（`:2464`，UPDATE 在 2481、commit 在 2506）——事务里删成片工作目录 + 整份剪映草稿。
4. **`_debug_sink`**（`v2_exporter/runner.py:269-279`）——`commit()` 失败被 `except: pass` 吞掉，**既不回滚也不提交**，未提交事务跟着连接跑完整个导出（默认 20 分钟、上限 120 分钟）。仅 debug 开关打开时才会走到。
5. **初始化路径**（`:218-239`）——`_initialize_connection` 无 try/finally；且"快速路径"仍会执行一条 `DELETE`（变更日志瘦身），在 343 万行那种规模下就是一个巨型删除事务。

**其它已确认（写下来避免重复投入）**：连接泄漏**没找到**（除 `_initialize_connection`）；跨线程复用没找到；`revenue_auto_scheduler.py:58` 纯 SELECT、**不是**元凶（印证了 09-17 那次"收益采集长事务"的判断确实是错的）；`execute_cleanup` / `queue_template_job` 都是**先删文件后写库**，不占写锁。

**只读判别方法（下次再现时用）**：用 `mode=ro` 只读连接每 2 秒查一次
`SELECT change_type, updated_at FROM v2_change_events ORDER BY id DESC LIMIT 1`——
触发器写在写者事务里，所以"卡住后恢复的第一条 `change_type`"直接指认是谁在写
（`production_task_changed` → 清理；`material_changed` → 扫描素材；`video_export_changed` → 导出）。
**生产库上不要执行** `PRAGMA wal_checkpoint` / `VACUUM` / `BEGIN IMMEDIATE`。
